# Delivering Task Follow-ups

`delivering-task-follow-ups <follow-ups file|directory>... [--review] [--run inline|background|window] [--agent claude|codex] [--parallel N] [--execution inline|subagents|direct] [--model M|cli-default] [--effort E|cli-default] [--reviewer-run background|subagent|window] [--reviewer-model M|cli-default] [--reviewer-effort E|cli-default]`

The root writes no code and no document of its own. It runs every phase as a [nested call](#nested-calls): `triaging-task-follow-ups`, `planning-task-docs`, `refining-task-docs` or `delivering-task` performed completely by a subagent, which reads that skill. The root reads none of them; the one rule it shares with them is its display copy [checkout.md](references/checkout.md). It decides what runs next and with which arguments, and reports. It asks no question of its own: every question of a run is a nested call's, relayed to the user.

`--run` places the orchestrator itself: by default (`inline`) this session runs it; `background` or `window` moves it to a child ([Run elsewhere](#run-elsewhere)). `subagent` is not a place for it, since its nested calls are subagents; it and any other value stop before anything starts, naming the value. Every other key goes to the nested calls as given:

- `--review`: to the triage, alone.
- `--agent`: to every `planning-task-docs`, `refining-task-docs` and `delivering-task` call. Without it none is passed: a nested call's subagent is this session's system, which each nested skill then takes as its own.
- `--model`, `--effort`, `--execution` and `--parallel`: to the `delivering-task` call, `--model` and `--effort` as explicit implementer values.
- `--reviewer-run`, `--reviewer-model` and `--reviewer-effort`: to every `refining-task-docs` and `delivering-task` call.

Each nested skill resolves its own role defaults, validates the values it receives and decides the execution mode; the root resolves no settings and decides no mode. The implementer runs in `delivering-task`'s default place unless the user's words set it ("implement without a window"): the root then announces the mapping and passes that place as `--run` to the `delivering-task` call. A child of [Run elsewhere](#run-elsewhere) takes it from its brief's `Implementer place:` line.

A **task** here is one brief the triage writes, followed through its plan, review and delivery. A task's **chain** ends at the first phase that does not reach its result; the other tasks go on.

## Run elsewhere

Under `--run background` or `window` this session is a thin launcher (run contract [Places](../child-sessions/references/run-contract.md#places)) and performs none of the sections below: a child of this session's system performs this skill `inline`, its nested calls included, and this session writes its brief, launches it, waits, relays its questions and reports its result.

1. **Before launch.** Read the installed `child-sessions/SKILL.md`, its `references/brief-writing.md`, `references/status-file.md` and `references/run-contract.md`; resolve its platform entrypoint by absolute path and set `<runtime>` from `runtime-dir`. Refuse before anything starts, naming the combination, what run contract [Refused combinations](../child-sessions/references/run-contract.md#refused-combinations) refuses for the place. Find the project checkout by [checkout.md](references/checkout.md) and resolve each argument to an absolute path.
2. **Settings.** Resolve the child's settings for role `orchestrator` per [launch settings](../independent-review/references/launch-settings.md#precedence): every field takes the role default, since `--model` and `--effort` set the implementer; resolve and pass the pair as launch settings [Places](../independent-review/references/launch-settings.md#places) says for the place. An unresolved or unsupported pair stops before launch, naming the place and the pair.
3. **Brief.** With `<slug>` as [Nested calls](#nested-calls) 1 names it: window `follow-ups-<slug>`, brief `<runtime>/follow-ups-<slug>-brief.md`, status `<runtime>/follow-ups-<slug>-status.md`, `background` run directories `<runtime>/follow-ups-<slug>-run-<n>`. A live window of that name is refused, naming it; leftover runtime files of those names are renamed `<file>-old-<n>`, `n` the smallest unused number. Write the run contract [brief](../child-sessions/references/run-contract.md#brief): `Skill:` this SKILL.md; `Arguments:` the absolute arguments and every key given except `--run` (`--model` and `--effort` stay: they set the implementer); `Checkout:` the project checkout; `Authority:` what this skill and its nested calls do with these arguments (the triage's fixes and its commit after the user's yes, windows, documents, commits, merges into main and cleanup), nothing more; `Place:`; `Auto: no`; `Status file:`; then the `Launch settings:` line of launch settings [Record](../independent-review/references/launch-settings.md#record), and, when the user's words set the implementer's place, the line `Implementer place: <place> (the user's words)`, the mapping announced to the user. Tell the child to read the Skill completely and perform it `inline` with the Arguments, within the Authority, and to write the status by status-file.md, `STATUS: done` once it has reported and `STATUS: failed` with the reason when it stopped, with its Report under a status section `## Report`, after the status contract's sections. Every nested call's question: in a `window` the child asks the user there; in `background` each question ends its turn with `STATUS: blocked` holding the question, options and its recommendation, and every turn ends with the status file written and its exact first line as the child's last message.
4. **Launch and wait.** Append the `Opened:` line, then launch and wait by run contract [Launch and wait](../child-sessions/references/run-contract.md#launch-and-wait): a `window` through child-sessions' `open --agent <this session's system>` with the pair, omitting a `cli-default` field; a `background` CLI with the pair and the [Permissions](../child-sessions/references/run-contract.md#permissions) arguments, since the child edits, commits and merges. Run the early child settings check at the first status after each opening; only a mismatch stops for the user's continue-or-stop question. A `blocked` status: show its Questions verbatim with options and recommendation, obtain the user's answer and continue by run contract [Questions and continuation](../child-sessions/references/run-contract.md#questions-and-continuation).
5. **Finish.** After `done` or `failed`, run the final [child settings check](../independent-review/references/launch-settings.md#child-settings-check), then report the status's `## Report` as this skill's Report (after `failed`, the failure and what the status lists), one settings line (role `orchestrator`, effective model and effort with their sources, the check outcome and record paths, or the user's acceptance) and, for `background`, each producer exit and session ID. After `done`, `close` a window; otherwise it stays with the status for the user.

## Preflight

1. **Checkout.** Find the project checkout by [checkout.md](references/checkout.md). Require it, and its separate docs repository when there is one (`<project>/docs/superpowers` with its own repository), each on its main branch, by a four-command boundary of [checkout state](../independent-review/references/checkout-state.md#direct-use-preflight) each, with process-local `GIT_OPTIONAL_LOCKS=0`; failed Git evidence stops. The small fixes land on main, and every merge goes there. Uncommitted changes are allowed and stay untouched. Staged changes in the main checkout hold every merge (`delivering-task` merges only while the index equals HEAD): when there are any, name them to the user now, as information, so that they can be committed or unstaged before the deliveries reach their merges.
2. **Skills.** Locate the installed `triaging-task-follow-ups`, `planning-task-docs`, `refining-task-docs` and `delivering-task` SKILL.md files by absolute path for the nested calls' `Skill:` lines, and read none of them: each nested call's subagent reads its own. Locate the installed `child-sessions` and read its [run-contract.md](../child-sessions/references/run-contract.md), [brief-writing.md](../child-sessions/references/brief-writing.md), [status-file.md](../child-sessions/references/status-file.md) and [platform-runtime.md](../child-sessions/references/platform-runtime.md); checkout state is `independent-review`'s. A missing one stops before anything runs, named for the user to install, so that no run stops for a missing skill after its triage commit. Each nested skill still checks its own dependencies when it runs. Resolve child-sessions' installed platform entrypoint by absolute path and set `<runtime>` from its `runtime-dir`. Announce the implementer's place when the user's words set it.

## Nested calls

Each `triaging-task-follow-ups`, `planning-task-docs`, `refining-task-docs` and `delivering-task` run below is a nested call by run contract [Nested calls](../child-sessions/references/run-contract.md#nested-calls):

1. **Brief.** `<slug>` is the first argument's file stem or directory name, with every character outside `[A-Za-z0-9_-]` replaced by `-`. Write the brief at `<runtime>/follow-ups-<slug>-<phase>-brief.md`, the status path `<runtime>/follow-ups-<slug>-<phase>-status.md` absent, `<phase>` being `triage`, `plan-<k>` or `refine-<k>` for task `<k>` in brief order, or `deliver`; an earlier run's file at either path is renamed `<file>-old-<n>` first, `n` the smallest unused number. It holds the run contract identity lines: `Skill:` the SKILL.md Preflight 2 located; `Arguments:` those the section names, every path absolute; `Checkout:` the project checkout; `Authority:` what that skill does with these arguments (the triage's fixes and its commit after the user's yes; the other skills' windows, documents and commits, and for `delivering-task` its merges into main and its cleanup), nothing more; `Place: subagent`; `Auto: no`; `Status file:`. It has no `Launch settings:` or `Opened:` line: a nested call takes the host's default settings, neither set nor verified, as run contract Nested calls says. Then these instructions, with the absolute status-file.md path filled in:

   ```text
   Read the Skill completely and perform it in this session with the Arguments as given, within the Authority; add no key, so that its workers take the places its Arguments and its own defaults give them. Run the skill completely, its windows included, and write its Report under a status section ## Report, after the status contract's sections. Write the status file by <absolute status-file.md>: STATUS: done once the skill has reported, STATUS: failed with the reason when it refused or stopped. Ask nobody directly: a question ends your turn with STATUS: blocked, its Questions holding the question, the options and your recommendation. End every turn with the status file written and its exact first line as your last message.
   Before the skill opens its first window, check that your shell tool can hold child-sessions' foreground wait (its foreground timeout reaches the wait's, or a yielded call can be polled until it exits). When it cannot, when a wait is refused or cut off before its timeout, when the host refuses a subagent the skill starts, or when the skill refuses a combination because this session is a subagent, stop there and write STATUS: failed whose reason starts "cannot hold the call:", naming what happened and every window, worktree and branch the skill left.
   ```
2. **Run.** Start a fresh subagent with the brief by the `subagent` bullet of run contract [Launch and wait](../child-sessions/references/run-contract.md#launch-and-wait), setting no model or effort, and wait until it ends. A subagent that ends without a valid first status line gets that section's one restart.
3. **Status.** `done`: read from `## Report` the items the section names. `blocked`: show the user its Questions verbatim with options and recommendation, obtain the answer and continue the same subagent by run contract [Questions and continuation](../child-sessions/references/run-contract.md#questions-and-continuation). `failed`: the nested skill refused or stopped; its reason and `## Report` go to the section's failure rule.
4. **Inline fallback.** A call the host cannot hold in a subagent runs `inline`: this session reads that SKILL.md then and performs it with the same arguments, as a direct run of that skill does, and Report names the call and why. The host cannot hold it when it has no subagent tool; when Codex's `[agents] max_depth` in the user's `config.toml` leaves no level below this session for the call's subagent, or for a subagent the nested skill's root itself starts (an implementer the user's words placed in `subagent`); when the host refuses the spawn; or when the call's status reason starts `cannot hold the call:`. Run contract [Host mechanisms](../child-sessions/references/run-contract.md#host-mechanisms) records a nested start and a subagent holding the wait loop as `unverified` on both hosts: attempt the subagent, fall back on a refused spawn or a `cannot hold the call:` status, and name the mechanism unverified in Report. After a fallback, later calls run `inline` at once for the same reason. A `cannot hold the call:` status naming a live window, a worktree or a branch the call left is not rerun: it ends the chain of every task in that call as a failed call does, naming those leftovers, which stay as they are (What remains gives the next command, `delivering-task <plan> --resume` for a delivery's branch or worktree); only later calls run `inline`.

## Triage

Nested call `triaging-task-follow-ups` with the given files and directories, plus `--review` when given. Read from its Report the finding table, its commit or `not committed: <reason>`, its review result when `--review` ran, and the brief paths in the order it lists them: the tasks are those briefs, in that order. A `failed` call (a stop or refusal there) ends the run: go to Report. With no brief, go to Report: every finding is fixed, dropped or kept.

## Plan and refine

For each task, in brief order, one task at a time, since the user answers each planner's questions in its window:

1. **Plan.** Nested call `planning-task-docs <brief>`, with `--agent` when given. Read from its Report the task's spec and plan paths.
2. **Refine.** Nested call `refining-task-docs <plan>`, with `--agent` and the reviewer flags when given. It adds the plan's spec by its own matching rules. Read from its Report each document's mark state (its new `Review:` line, `fresh, context only` or `not marked: <why>`) and the open findings.

A nested call that ends `failed`, or `blocked` without the user's answer, ends that task's chain, recorded with the skill and its reason; a `cannot hold the call:` status is no failure but [Nested calls](#nested-calls) 4's fallback, unless it names leftovers. Nothing a phase left (window, status, documents) is undone. A refine whose Report leaves the plan `not marked` ends the chain too, with the open findings it names: an unreviewed plan is not delivered. Go on with the next task.

## Deliver

The tasks whose refine Report shows the plan with a `Review:` mark (a new one, or `fresh, context only`) are delivered together in one nested call: `delivering-task <plan>...`, their plans in brief order, with `--agent`, `--execution`, `--model`, `--effort` and the reviewer flags when given, and `--run` with the implementer's place when the user's words or the brief's `Implementer place:` line set it. One plan runs `delivering-task`'s one-document path; its stops and questions are that path's own. Several plans run its queue, with `--parallel` when given and with `--independent`, since every triage group is a task independent of the others; `--independent` is not passed for one plan, which `delivering-task` refuses it for. A `**Depends on:**` line a planner wrote still counts as the queue says. Every other question of the queue (an already merged unit, leftovers to resume or discard) is the queue's own, relayed as every nested call's question is. Read from its Report, for each plan, the merge SHA or ready branch, or its state with the worktree and branch it kept; the follow-ups path and count; and the settings lines. With no task to deliver, go to Report.

## Report

- The triage's finding table (`# | file | class | outcome`), its commit or `not committed: <reason>`, and its review result when `--review` ran.
- A table of the tasks: `task | brief | spec | plan | refine | delivery | merge SHA | follow-ups count`, each phase's outcome as its nested call's Report gave it, `-` for a phase the chain did not reach, and the reason where a chain ended. The follow-ups count comes from the delivery's Report for each delivered task.
- The settings lines of the delivery's Report, and one line for the nested calls themselves: `subagent` with the host's default settings, not verified, and each call that ran `inline` with its reason and the `unverified` host mechanism it met.
- What remains, as commands to run by hand:
  - each task whose chain ended, with the next skill for it (`planning-task-docs <brief>`, `refining-task-docs <plan>`, `delivering-task <plan>`, or `delivering-task <plan> --resume` when its delivery left a branch or worktree), and where to look (the nested call's brief and status file, and the status file and window its Report names);
  - each follow-ups file still holding kept findings, with its count of `- ` lines;
  - each follow-ups file the delivered tasks left, for another `delivering-task-follow-ups` run. This run does not take them up itself.
