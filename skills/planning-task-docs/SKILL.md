# Planning Task Docs

For each clean/path gate and continuation below and in child briefs, use the four ordinary Git commands and identity checks in [checkout state](../independent-review/references/checkout-state.md#direct-use-preflight), with process-local `GIT_OPTIONAL_LOCKS=0`, actual exits and raw output files. These are own-paths gates over the spec and plan in the repository holding them; unrelated staged or unstaged paths pass and stay untouched. A repository holding neither document owns no path. A clean gate requires successful commands and empty status and diffs; path gates parse NUL-delimited status and compare exact repository-relative paths, including both rename paths. Failed or unavailable Git evidence stops the dependent action. Use ordinary Git for other read-only checks, retaining real exits. Evidence has the reference's ignored/untracked-content, Git flags/normalization, nested-repository and transient-write limits. Stage/commit only owned paths; write, merge and push authority stays explicit.


`planning-task-docs <"task text"|brief|spec|follow-ups file> [--run window|inline|subagent|background] [--agent <claude|codex>[:<command>]] [--model M|cli-default] [--effort E|cli-default] [--auto]`

One task per run. The planner writes the documents with superpowers `brainstorming` and `writing-plans`, and `--run` places it ([Launch](#launch)). By default it is a child in a `window`, a visible session where it talks to the user, who answers its questions there, never through the root; a child in a `subagent` or `background` asks every question through the root; under `inline` this session is the planner. The root classifies the input, runs the planner in the project checkout, waits, verifies Git/status facts and reports paths. Outside `inline` it writes no document, mark or commit and never edits a child status. It invokes no other task skill: the user chooses what runs next. A stop placed "before any window" below comes, in every place, before the planner starts.

Under `--auto` read child-sessions' [auto.md](../child-sessions/references/auto.md): the brief says `Auto: yes`, so the planner asks nobody, in its window either, and each question it cannot settle by auto.md's [Deciding](../child-sessions/references/auto.md#deciding) step 1, brainstorming's and the spec's approval included, reaches the root as `STATUS: blocked`; the root routes it and every question below that would go to the user by auto.md's Deciding, and the report lists `## Decisions`.

## Phases

A session performs Prepare, Wait and Accept in order as one root. A session whose brief or prompt carries `Phase: prepare` or `Phase: accept` performs that phase alone and ends as that brief says, naming the record's path. Without a `Phase:` line, continue from Launch to Wait and Events yourself; do not end after Prepare. `--run inline` follows Inline instead, with no phases or record.

| Phase | Who performs it | Sections to read and perform | References to read |
|---|---|---|---|
| Prepare | The single root, or the Prepare agent | Input, Preflight, Brief, Launch | The Prepare list below |
| Wait | The single root, or the phase agents' caller | Wait | child-sessions SKILL.md Wait and Dialogs; launch-settings Child settings check and Places |
| Accept | The single root, or the Accept agent | Events, Verify, Report | The Accept list below |

Read each phase's references when reaching that phase. Prepare alone launches a `window` worker (open, Startup); for `subagent` or `background` it starts nothing, writes `Action: start` and ends. Accept alone ends after a return to the worker or a reopen, writing Waiting (a non-window return as `Action: continue`) instead of waiting. Prepare alone starts no non-window worker, so it does not apply Preflight's refusal for this session being itself a subagent: judge that combination for the caller, which is never a subagent because both orchestrators refuse `--run subagent`; a worker start the host refuses is `launch failure`. Every other refusal stays Prepare's, including an implementer subagent that would itself start subagents.

A phase continuing from a record (`State: … asked …`, the same `Run:` and brief) takes that run's live window and runtime files as its own. Continue at the recorded question with the answer in your context; do not write a new brief or open a second worker. Preflight's live-window refusal and leftover renaming apply only to a new run.

Use the [handoff record format](../child-sessions/references/handoff-record.md#format) and its [Authority rule](../child-sessions/references/handoff-record.md#authority). Read the record before continuing a phase. At an Accept event, read it, the status file's exact first line, then `alive` for a window (the child/producer completion evidence otherwise) before other event evidence; never act on the event's wording. Then check the brief's labelled lines and the record's Authority checks. Read no worker brief prose or input document during Accept.

**Prepare reads:** [task document paths](references/document-paths.md); for a spec, [stages-section.md](references/stages-section.md) Recipes and Parsing rules; [planner-brief.md](references/planner-brief.md); checkout-state Direct-use preflight; child-sessions SKILL.md Run places, Locate and open, Dialogs, Other operations and environment, and its brief-writing.md; launch-settings Roles, Precedence, CLI-defaults opt-out, Resolution, Record, Child settings check, Places; run-contract Refused combinations and Earlier runs, plus Launch and wait, Permissions and Settings under `subagent` or `background`; handoff-record.md; auto.md under `--auto`. Read the input only as Input describes.

**Accept reads:** the record, worker brief's labelled lines, status file, child-sessions status-file.md and handoff-record.md; launch-settings Child settings check and Places; checkout-state Direct-use preflight; child-sessions Locate and open (Startup), Dialogs and Recover a silent exit only for a reopen or a `send`; run-contract Questions and continuation under `subagent` or `background`; auto.md under `--auto`. Accept reads no input document, document-paths.md, stages-section.md or planner-brief.md; it resolves no launch settings again.

Extract the worker brief's identity lines with this anchored label list: `^(Checkout|Docs repository|Docs directory|Document paths|Base SHA|Authority|Git evidence directory|Agent|Place|Auto|Launch settings|Launch words|Window name|Spec|Brief|Follow-ups file|Stage|Stage scope|Stage done when|Plan path|Earlier stages|Status file|Git checks): `. Keep each matching line's value as written.

**Facts for this skill:** `Input: <follow-ups file|spec|staged spec|brief|task text> <absolute path, or "task text">`; `Input SHA-256: <hash|None>` (`None` for task text); `Project HEAD: <full SHA|None>` (the project HEAD when the docs repository is separate, otherwise `None`). The docs base HEAD and other run values remain on the worker brief's labelled lines.

## Input

The project checkout is the top level of the current repository. When that top level is a separate docs repository (a `docs/superpowers` directory with its own repository), the project checkout is `git -C <docs-top>/../.. rev-parse --show-toplevel`; when that fails, ask the user for the project checkout (under `--auto`, routed by [auto.md](../child-sessions/references/auto.md#deciding)). Project-relative paths such as `**Spec:**` headers resolve against the project checkout, never the docs repository. Resolve the input without reading it through: use its name and place, and line searches for `> **For agentic workers:** REQUIRED SUB-SKILL:`, `**Spec:**` and `**Stage:**` headers. Count a follow-ups file's `^- ` findings; for a spec run `stages_parse`, and for a staged spec read the next stage's `**Scope:**` and `**Done when:**` lines. Compute SHA-256 with a tool. Read [task document paths](references/document-paths.md) for location/kind, pairing and discovered candidates. Classify it by the first rule that matches; every stop happens before any window:

1. **Follow-ups file**: a file whose name ends `-follow-ups.md`, or `-tails.md` (the older format of the same file). Each line starting with `- ` is one finding. With none, report "nothing to plan" and stop.
2. **Plan**: it is a plan by task document paths. Refuse: "already planned; review it with `refining-task-docs` or execute it with `delivering-task`".
3. **Spec**: it is a spec by task document paths. Run `stages_parse` from [references/stages-section.md](references/stages-section.md#recipes) on it, then follow its exit:
   - Exit 1 with stderr exactly `no "## Stages"`: the spec is unstaged. Find its plans by task document paths, with no question. Any found: report "already planned", naming each plan, with the same pointer to `refining-task-docs` or `delivering-task`, and stop. None: the child writes the plan only.
   - Any other exit 1: the spec's `## Stages` section is broken. Stop, naming the failed rule: the stderr line and the Parsing rule that words it. Exit 2: stop, reporting the stages evidence unavailable with the stderr reason.
   - Exit 0: the spec is staged; stdout lists its stages. Apply the Parsing rules of [stages-section.md](references/stages-section.md#parsing-rules) using the stage directory and candidates from task document paths, with no question. The spec's plans are the candidates (follow-ups and tails files excluded) that are the naming pair, carry a `**Spec:**` header naming this spec, or have a stem starting with `<spec-stem>-NN-` for a stage NN of the section and belong to no other spec, as Stage matching says: a plan found only by its file name counts. Then apply, in order: Stage matching, which stops on a plan matching two stages, naming it and both stages, and on two plans matching one stage, naming both; Unstaged plan, where an unstaged plan stops, naming it: "staged spec with an unstaged plan; remove or stage the plan"; Next stage. With no next stage, every stage is planned: report "already planned", naming each stage plan, with the same pointer to `refining-task-docs` or `delivering-task`, and stop. When the next stage's Stage plan path already exists, stop before any window, naming the stage and the path: "stage NN's plan path holds another spec's plan; rename the stage or that plan". Else the child writes the next stage's plan only, at its Stage plan path.
4. **Brief**: any other existing file.
5. **Task text**: a quoted text that is not an existing path.

`<slug>` is the input file's stem; for a staged spec, `<slug>` is `<spec-stem>-<NN>-<stage-slug>` of the next stage (window `plan-<slug>`); for a task text, `<today>-<slug>` with `<slug>` made of `[a-z0-9-]` from its key words (`Add a --version flag` → `2026-11-01-version-flag`). Replace every character outside `[A-Za-z0-9_-]` with `-`.

## Preflight

1. Resolve applicable project rules and the project checkout. Define absolute `docs_dir` as the rules' documentation destination, defaulting to `<project>/docs/superpowers` even when absent. Derive the intended absolute output paths before any repository-relative conversion: for an unstaged spec input, only `<stage-directory>/<spec-stem>.md` using task document paths' same-directory sidecar or mirrored stage directory; for a staged spec, the next stage's exact Stage plan path (Input rule 3); for other inputs whose `<slug>` starts with `YYYY-MM-DD-`, `<docs_dir>/specs/<slug>-design.md` and `<docs_dir>/plans/<slug>.md`. For remaining inputs, resolve the intended spec and plan names under `<docs_dir>/specs/` and `<docs_dir>/plans/` from the actual input and project rules, preserving brainstorming's and writing-plans' existing naming conventions; bind those absolute paths before proceeding to the gates. The input spec remains read only. Keep Input's existing plan and stage-path collision stops.
2. Locate the installed `child-sessions/SKILL.md`; read its Run places, Locate and open, Dialogs and Other operations and environment sections, plus brief-writing.md. Prepare names the status-file.md path in the brief but leaves reading that contract to the worker and Accept. Resolve its installed platform entrypoint by absolute path (Bash `scripts/child-session`; native Windows `scripts/child-session.ps1` through the installed PowerShell vector in its platform reference). Its command/status contract governs every call. Set absolute `<runtime>` from successful `runtime-dir` output; unavailable resolution stops dependent preparation. Do this under `inline` too, for evidence storage only: resolve no terminal backend or launch settings there.
3. Allocate a fresh uniquely named evidence directory under `<runtime>`, with separate `root/` and `child/` subdirectories; bind their absolute paths now. Keep it outside every monitored project and document repository, confirming the document repository in step 4 before captures. Every root Git boundary gets a fresh named directory below `root/`; the child's boundaries go below `child/`. Keep this evidence separate from background producer run directories, retain older evidence, and never reuse or rename another run's evidence. Runtime-only preparation may precede later place/settings refusals: it launches no worker or backend and creates no project document.
4. Resolve the document repository: when `docs_dir` exists, require successful `git -C <docs_dir> rev-parse --show-toplevel`; when absent, use the project repository without creating `docs_dir` to classify the run. Allow the project repository, or a separate repository rooted at the existing docs destination; another destination/repository requires explicit applicable project-rule authority. Require every intended absolute output inside that authorized repository and convert it to its exact repository-relative owned path; refuse any other mapping rather than guessing. A separate repository at `<project>/docs/superpowers` owns `specs/2026-11-05-sample-design.md`; tracked or absent `<project>/docs/superpowers` in the project repository owns `docs/superpowers/specs/2026-11-05-sample-design.md` (and the corresponding `plans/` path). For each output run `git -C <selected-repository> check-ignore --quiet -- <exact-relative-path>`, retaining actual exits and outputs below the root evidence directory: 0 means ignored, 1 unignored, any other exit unavailable. Ignored or unavailable output checks stop before any worker launch or document write, inline included; for ignored output ask for an authorized trackable destination or separate docs repository. Do not force-add, initialize a repository or change ignores.
5. With fresh boundary directories below the root evidence directory, verify checkout/branch/HEAD identity and run the four-command own-paths gates on the repositories holding the intended documents, using only those exact relative output paths. A hit stops, naming the path; unrelated staged or unstaged work passes and stays untouched. Record the full HEAD of the docs repository and, when separate, the project checkout. For a brief, spec or follow-ups input, record the input file's SHA-256.
6. Decide the place and the agent. The place is `--run`: `window` when absent, also under `--auto`, else `inline`, `subagent` or `background`; the user's words choosing a place count as the key, and any other value stops. Announce a place other than `window`. Select `--agent`, a value that may carry a [launch command](../child-sessions/references/run-contract.md#launch-command), otherwise identify the root's own system from session identity as independent-review's [Session system](../independent-review/SKILL.md#session-system) does; unknown identity requires clarification (under `--auto`, routed by [auto.md](../child-sessions/references/auto.md#deciding)). Never infer the agent from executable availability, environment, directory names or model. Refuse before any worker launch or document edit, naming the combination, what run contract [Refused combinations](../child-sessions/references/run-contract.md#refused-combinations) refuses for the planner: under `inline`, an `--agent` naming a system other than this session's or an explicit `--model` or `--effort`; under `subagent`, an `--agent` naming a system other than this session's, or this session being itself a subagent on a host whose subagents cannot start subagents.
7. Under `inline` resolve no settings: the planner is this session ([launch settings Places](../independent-review/references/launch-settings.md#places)). Otherwise read launch-settings' Roles, Precedence, CLI-defaults opt-out, Resolution, Record, Child settings check and Places; read run-contract's Refused combinations and Earlier runs, and under `subagent` and `background` its Launch and wait, Permissions and Settings sections. Resolve the planner's settings per [launch settings](../independent-review/references/launch-settings.md#precedence) for the selected agent: `--model`/`--effort` are explicit values, `cli-default` is a per-field [opt-out](../independent-review/references/launch-settings.md#cli-defaults-opt-out), and every other field takes the planner role default. An unresolved or unsupported pair stops before any window. Under `subagent` and `background`, resolve and pass the pair as launch settings [Places](../independent-review/references/launch-settings.md#places) says for the place; a pair the place cannot select is refused before launch, naming the place and the pair.
8. Check the selected child's actual installed catalogs, this session's own under `inline` (Claude: `~/.claude/skills`, enabled `~/.claude/plugins`; Codex: `~/.codex/skills`, `~/.agents/skills`, enabled `~/.codex/plugins`; plus the project's `.claude/skills` and `.agents/skills`). Resolve readable absolute SKILL.md paths for superpowers `brainstorming` (not needed for a spec input) and `writing-plans`. Executables or the root's catalog alone do not prove child skill availability. A missing one stops before any window: ask the user to install superpowers for that agent. No other skill substitutes for them.
9. For an unstaged file input, `<slug>` is its complete filename without the `.md` extension, including a final `-design` when present: `sample-design.md` gives `plan-sample-design`. Staged specs and task text use Input's own slug rule. Outside `inline`: window `plan-<slug>`, brief `<runtime>/plan-<slug>-brief.md`, status `<runtime>/plan-<slug>-status.md`, handoff record `<runtime>/plan-<slug>-handoff.md`, and for `background` run directories `<runtime>/plan-<slug>-run-<n>`. For a new run only, a live window of that name (`alive plan-<slug>` returns 0) is refused, naming it. Leftover runtime files of that name from an earlier run (brief, status, handoff record, their archived `-blocked-<n>` and `-rejected-<n>` copies, and run directories) are renamed, for a new run only, to `<file>-old-<n>`, `n` the smallest unused number, after the check of run contract [Earlier runs](../child-sessions/references/run-contract.md#earlier-runs); no file exists at the status path when the brief is written. Evidence directories are retained separately and excluded from this renaming.

## Brief

Outside `inline`, fill [planner-brief.md](references/planner-brief.md) with absolute resolved document paths and the child evidence directory bound in Preflight 3, the place of Preflight 6 and `Auto:` (`yes` under `--auto`), following child-sessions' brief checklist, and write it to the brief path. Substitute every labelled field, including `Task document paths:` as this skill's installed `references/document-paths.md` absolute path, `Authority:` and `Git evidence directory:`; narrow Authority and Ownership to the actual outputs (plan only for a spec input), keeping any input spec read only. Work, Authority, Ownership and Boundaries must agree. Immediately after writing the brief, create the handoff record with `State: prepare: brief written`, its identity and Facts lines, and any Report carries or Decisions already made.

A `window` brief's `Terminal controls:` line is the template's fixed text: the brief is written before `open`, when no launch exists to report a backend or controls. After every `open` (the first, a reopen, a resume), read that launch's `capabilities <name>` and check its checkout/launch identity before any terminal control; every `peek`, `send` and `key` below is conditional on the current launch's supported capability, never on the brief, and nothing about controls is written into the brief or sent to the child. When the current launch's record lacks `peek`, `send` or `key`, read Told the user and, unless its notice for this launch is already there, tell the user that questions/dialogs need direct attention in that window and append `<launch>: terminal controls unavailable, direct attention` to Told the user, then continue through brief/status files; report dialog counts as not observable. A known `blocked` question still follows the status contract, with its answer entered directly by the user when `send` is unavailable. Under `--auto` the root still decides that answer by [auto.md](../child-sessions/references/auto.md#deciding) and records it; the user is asked only to type that given answer into the window, and the report names the missing `send` as the backend's limitation. A timeout alone supplies no question or approval. Check `alive` before any supported input; never reopen a live agent to inject text. Reopen a proven dead launch at most once under the shared budget below. `close` stops only proven owned processes; unavailable window closure leaves a reported retained window, whose shell alone is not a live agent.

## Launch

Run the planner in the place Preflight 6 decided.

### Window

1. Call `open --agent <agent> [--model M] [--effort E] [--cli-arg WORD]... --split right plan-<slug> <project checkout> <brief>`, quoting paths, passing the brief's recorded Launch settings as `--model` and `--effort` and omitting a field that is `cli-default`, and for a Claude agent the run contract's [lean launch](../child-sessions/references/run-contract.md#launch-and-wait) words as `--cli-arg` values. Write these words on the brief's `Launch words:` line and the handoff record's [`Launch words:`](../child-sessions/references/handoff-record.md#format) line before the launch (a root that writes no record keeps them on the brief) and pass the same words on every reopen and resume, a `--session-id` word with a fresh UUID. The user answers the child's questions in its window (under `--auto`, only watches it), so it asks for a pane right of the root; when `open` prints a fallback note (a tab or a tmux window instead), tell the user where the window opened. The child works in the project checkout: no worktree, no branch of its own. Tell the user that the run owns the task's documents: edit neither the input file nor the spec and plan being written while the window is open; any other file stays theirs to change and commit.
2. Read this launch's capabilities and perform child-sessions' Locate and open **Startup**.

### Subagent and background

For Prepare alone, do not start this worker: record the start recipe below as `Action: start <place>` in Waiting, with the brief, checkout, settings and permission arguments, then complete Launch Record and end. The caller records the actual opening and performs the start; a single root performs it here.

1. Start the planner in the project checkout by run contract [Launch and wait](../child-sessions/references/run-contract.md#launch-and-wait): a `subagent` with the pair Preflight 7 resolved, set by the host's native controls; a `background` CLI with the brief's recorded Launch settings, omitting a field that is `cli-default`, and the permission arguments of run contract [Permissions](../child-sessions/references/run-contract.md#permissions), since the planner writes and commits. Each `background` start or resume writes its run directory at `<runtime>/plan-<slug>-run-<n>`, `n` the smallest unused number. Tell the user that the run owns the task's documents until it reports, as Launch Window 1 words it. The child works in the project checkout: no worktree, no branch of its own.

### Record

Complete the [record](../child-sessions/references/handoff-record.md#format): `State: prepare: launched`, Facts, Report carries, Decisions and Told the user. Before the ownership notice in Launch Window 1 or Subagent and background 1, check Told the user; give it once and record `documents owned by the run`. Carry launch fallback/place notices and dialog counts too. Waiting lists the worker and `Action: none` after an actual start, or the phase-alone non-window start recipe. Prepare alone ends as its brief says, naming the record; a single root continues to Wait.

## Wait

The single root holds the wait; for phase-alone agents their caller holds it. Follow child-sessions' [Wait](../child-sessions/SKILL.md#wait) for `plan-<slug>`, using the rung it proves or its present loop with the host-specific duration, explicit tool timeout and same-command polling. When choosing the rung, write its report line to the record's `Wait:` and set `State: waiting`. For `subagent` and `background`, wait as run-contract Launch and wait says; complete background recording before reading terminal status.

Brainstorming with the user can take long: keep waiting; on a free rung each quiet stretch costs one stall wake.

The wait holder handles these events without starting Accept:

- **`blocked`:** show Questions verbatim with its options and recommendation and obtain the user's answer (under `--auto`, route it by auto.md's Deciding; without `send` the user only types it in, as Brief says). Archive the status to `<file>-blocked-<n>`. For a window, apply Events **Before every send**, send one line or an absolute answer-file instruction, then wait for a fresh status. A dead worker before that send goes to Events **Reopen**, carrying the line to send. For `subagent` or `background`, continue the same child by run-contract Questions and continuation, or its fresh-child fallback; update Waiting, then wait again.
- **`124` or `4`:** `peek plan-<slug> 40` when supported; wait again for work in progress, handle a dialog per child-sessions Dialogs, or apply Wait's stall rule and re-arm. Preserve the rung and one-watcher rule. A timeout supplies no question or approval.

Everything else goes to Events. Other command errors stop with artifacts preserved. Keep changed facts, Report carries, Decisions and one-time notices in the record.

## Events

Accept starts from evidence: read the record, the status file's exact first line, then `alive plan-<slug>` for a window (the child/producer completion evidence otherwise). Then validate the record against the brief's labelled lines and runtime evidence by its Authority rule, even when the caller supplied an event description.

- **`done`:** proceed to Verify.
- **`failed`:** show the failure and stop, keeping the window/status or status/run directories; the report says no spec and plan were produced and lists any commits the status names.
- **Silent exit:** the window worker is gone or the child ended, with no valid first status line. Follow Reopen below. A launch failure gets no restart: stop with its diagnostics and artifacts preserved.
- **`blocked`, a deadline or a stall:** handled by Wait, not as successful completion.

For **Accept alone**, the caller may report three further events. `Event: deadline`: take the evidence above first; a valid status takes its own row, and `alive` exit `1` is Silent exit. A live worker without a status adds `<launch>: no status at the wait's deadline, still working` to Report carries, leaves Waiting as it is and ends `waiting`. `Event: dead before send`: apply Before every send's dead branch with the phase brief's `Line to send:`, then end `waiting` after a successful reopen; its existing stop still applies when the shared reopen is spent. `Event: launch failure`: stop by this skill's launch-failure rule with the phase brief's Diagnostics, preserve the artifacts and end `failed`.

**Reopen.** Read `Reopen:` from the record. With `unused`, for a window `peek plan-<slug> 40` when supported and show diagnostics. Append this continuation line to the brief:

> Continue from the current state of the checkout: read git log and record the ordinary Git evidence and verify checkout/branch/HEAD first. Uncommitted changes on your owned paths are your earlier session's work: inspect them and continue from them.

Close the stale owned window if present, confirm the worker is dead, then `open` as Launch Window 1 with the brief's recorded Launch settings and the record's `Launch words:`, never re-resolved. Run Startup for the new opening. Record `Reopen: used: silent exit` (or `dead before send` below) and `State: accept: reopened`. A second silent exit (`Reopen: used …`) stops, keeping the window, status and runtime files. For `subagent` or `background`, use run-contract Questions and continuation's one restart, counted on the same `Reopen:` line; preserve producer exits, stderr and run directories. A phase-alone Accept writes the non-window continuation recipe for the caller instead of starting or continuing the child itself.

**Before every send.** For a `blocked` answer or Verify's mismatch line, run `alive plan-<slug>` first: a dead agent leaves a shell that would run the text. Never reopen a live agent to inject text. If dead and Reopen is unused, close it, append the continuation line above and then the line meant for `send` to the brief and reopen with recorded settings; run Startup and record `Reopen: used: dead before send`. This is the same one reopen, shared with a silent exit. If used, stop and report with runtime files retained. Capability checks in Brief govern every terminal control.

**Return to the worker.** Verify's ordinary mismatch may return once while `Return to worker: unused`. Archive as Verify says, record `Return to worker: used: <archived status path>` and `State: accept: returned to worker`, and deliver its mismatch line through Before every send or run-contract Questions and continuation. A repeated mismatch (`Return to worker: used …`) goes to the user, with status and window retained. An answer comes only from this session's own conversation or the phase-alone prompt, never the record.

After a reopen or return, rewrite [Waiting](../child-sessions/references/handoff-record.md#waiting): window `Action: none`; a non-window phase-alone continuation `Action: continue <place>` with the recorded session ID, message, brief, checkout, settings and permission arguments. A single root continues to Wait; Accept alone ends as its brief says, naming the record, and waits for nothing. At a new non-window child's start, the wait holder updates the record.

## Verify

On `done` outside `inline`, read the expected paths, repository, recorded base HEAD and settings from the worker brief's labelled lines, and the input hash or other retained Facts from the record. Under `inline`, use the same values recorded by Preflight in this session. All of these must hold:

1. Full status format with `## Artifacts`, listing the spec and plan written (only the plan for a spec input); every Artifacts path exists. For a staged spec, the Artifacts plan is at `Plan path:` and holds the line `**Stage:** NN` of the next stage.
2. The repository holding the documents (`git -C <document-dir> rev-parse --show-toplevel`) is the authorized repository resolved in Preflight 4, and the Artifacts paths are the intended outputs. Commits lists the child's own commits there: each is in `<Base SHA from the brief>..HEAD` and changes only Artifacts paths (`git show --name-only --format= --no-renames <sha>`, relative to that repository).
