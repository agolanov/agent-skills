# Executing Task Docs

For every checkout cleanliness or changed-path gate below and in child briefs/references, use [checkout-state Direct-use preflight](../independent-review/references/checkout-state.md#direct-use-preflight). Resolve its installed helper, retain fresh evidence, and require `uncommitted: false` for clean. Unavailable verification stops the dependent action; raw status/diff is not a fallback. Path allowlists use the result's decoded exact `paths`. This applies separately to project, docs and child checkouts. Every read-only Git verification below and in references/child briefs (log, refs, roots, ancestry and diffs included) uses that reference's `git-read` command; displayed `git <read-command>` notation means this wrapper, never a raw invocation. Resolve paths relative to the containing checkout root. Mutating commands keep their explicit authorization.


`executing-task-docs <task-document> [--spec <spec>] [--agent claude|codex] [--model M] [--effort E] [--branch B] [--resume]`

The child owns implementation and refinement. The root checks Git/status facts and records follow-ups the child cannot commit; it does not write product code, add commits to the task branch, or repeat the child's tests or review. The run ends with a verified branch ready to merge.

## Preflight

1. Resolve the main checkout, main branch, the absolute task document path, and applicable project rules. Require the main checkout on its main branch with a clean preflight. Recognise the document and read it completely:
   - **Plan**: it carries the superpowers plan header (`> **For agentic workers:** REQUIRED SUB-SKILL:`) or lies in a `plans/` directory of a superpowers docs dir (`docs/superpowers/plans/`) and is not a `*-follow-ups.md` or `*-tails.md` file. Spec: `--spec`; else `<plan-stem>-design.md` beside the plan or in the sibling `specs/` directory; else the plan's `**Spec:**` header (path relative to the project checkout); else `None`, with no question.
   - **Spec**: named `*-design.md` or lying in a `specs/` directory. Find its plans in the sibling `plans/` directory by the matching rules: the naming pair (`specs/YYYY-MM-DD-<slug>-design.md` with `plans/YYYY-MM-DD-<slug>.md`), then every plan whose `**Spec:**` header names this spec. None: refuse before any worktree or window, telling the user to write the plan with `planning-task-docs`. One: that plan is the task document, this spec its spec. Several: list them and ask the user which one to execute.
   - **Other**: any other file is a task document implemented directly (a brief, a task text). Spec `None`.

   `--spec` is accepted only with a plan. Layout: the docs repository is `git -C <document-dir> rev-parse --show-toplevel`, named by its main-checkout absolute path. **Tracked**: it is the project and `git -C <main-checkout> check-ignore -q <document-dir>` exits non-zero. **Separate docs**: it is another repository (nested in an ignored directory or elsewhere); require its main checkout on its main branch with a clean preflight. **Ignored**: it is the project and that `check-ignore` exits 0 (ignored without its own repository). Show the user the document's kind, its spec and the layout, and the review-mark state of the task document and its spec per [review-mark.md](references/review-mark.md): fresh with verdict, reviewer and date; else `none` or `stale` with the failing freshness condition. The mark state is information only; continue whatever it is.
2. Select `--agent`, otherwise identify the root's own system from session identity as `auto-cross-refine` does; unknown identity requires clarification. For `--resume`, recover recorded launch identity subject to the provenance checks below; conflicting explicit overrides stop. Never infer the agent from executable availability, environment, directory names, or model. Default branch to the task document's stem (the plan's stem for a plan or a spec resolved to its plan); validate with `git check-ref-format --branch`, asking for a valid override if invalid. Use window `<name> = impl-<branch>` for `[A-Za-z0-9_-]+` branches; otherwise replace disallowed branch characters with `-` and use `impl-<slug>-<hash8>` (first eight SHA-256 hex characters of the full branch name). Record the unique name; never alias slash/dot branches by slug alone.
3. Locate root's installed `child-sessions/SKILL.md`; read it and its owned `references/brief-writing.md` and `references/status-file.md`. Resolve its executable relative to that SKILL.md as `scripts/child-session`, never through PATH. Its command/status contract governs every call below.
4. Check the selected child's actual installed catalog/directories: Claude's `~/.claude/skills`, enabled `~/.claude/plugins`; Codex's `~/.codex/skills`, `~/.agents/skills`, enabled `~/.codex/plugins`; plus project `.claude/skills` and `.agents/skills` available to that child. Resolve readable absolute paths for `auto-cross-refine`, the opposite-system launcher (`refine-with-codex` for Claude, `refine-with-claude` for Codex), `review-fix-loop`, `independent-review`, `writing-task-follow-ups` in the tracked layout, and, for a plan, every installed one of `executing-plans`/`subagent-driven-development` (at least one is required). Verify checkout-local paths remain available in the worktree. Executables or the root's catalog alone do not prove child skill availability. In the separate-docs and ignored layouts, also locate the root's own installed `writing-task-follow-ups/SKILL.md`. Missing dependencies stop before opening; report them for the user to install, without substitution.

## Worktree

1. Use the project worktree convention, otherwise `<main-checkout>/.worktrees/<branch>`. Resolve the main checkout and selected path, including existing symlinks. For a path inside the main checkout, run `git check-ignore`; if it is not ignored, tell the user and stop without changing ignore rules. For an external path, apply the same ownership/existence checks without an ignore prerequisite. Refuse any existing branch or worktree, naming both, unless `--resume`.
2. For a new task record full main HEAD as `<base-sha>` and run `git worktree add -b <branch> <path> <base-sha>`. Verify its branch and HEAD match. Keep runtime files under `${XDG_RUNTIME_DIR:-/tmp}/child-sessions/` outside Git, creating parent directories for nested branch names.
3. For `--resume`, require the prior runtime brief with base, absolute task document/spec identity (a brief written by `deliver-task` names the task document on its `Plan:` line), branch, checkout, window name and launch options. Match it to the requested task and registered Git worktree/branch; validate the recorded base exists and belongs to the task history. Reuse the recorded base/window identity, never today's main as a guessed replacement. Missing, conflicting or ambiguous provenance stops. Preserve current work for the child, archive any prior status to an unused suffix. A `deliver-task` brief has no `Follow-ups:` line: append the current template's `Follow-ups:` line, filled as Brief 1 says, and its follow-ups paragraph, which replace the brief's tails sentence, and the sentence “In Review, name the full SHA of the last commit the review covered as `Reviewed HEAD: <sha>`.” Then append “Continue from the current state of the checkout: read git log and run the checkout-state preflight first.” An old terminal report cannot complete a resumed run.

## Brief

1. Read [implementer-brief.md](references/implementer-brief.md), fill every placeholder, and write `<runtime>/<branch>-brief.md`; status is `<runtime>/<branch>-status.md`. Persist task identity/base and selected launch options for resume. Resolve required skill paths for the child's actual checkout/catalog, and provide the absolute owned status-contract path. Fill Layout facts: docs repository as Preflight 1 found it, named by its main-checkout absolute path even when it is the project itself; Follow-ups in the tracked layout is the absolute `<document-stem>-follow-ups.md` path beside the task document inside the worktree plus the child's `writing-task-follow-ups` SKILL.md, otherwise `the root records them`; ignored test material is the test path the project rules state, else `tests/`, resolved against the main checkout to an absolute path; use it when it exists and `git -C <main-checkout> check-ignore -q <path>` exits 0, otherwise `None`. A stated path that fails either check is `None`, never replaced by `tests/`; before opening, tell the user which path failed which check. Follow child-sessions' self-contained brief checklist.
2. Keep the exact `Status file: <status-file>` line. A new task requires an absent status path; an existing artifact needs provenance validation or a stop, not silent reuse. Only the child writes status contents.

## Open and wait

1. Call the resolved script: `open --agent <agent> [--model M] [--effort E] <name> <path> <brief>`, quoting paths. On explicit resume reuse the recorded window/options and continuation brief; close any owned stale window before reopening, never an unrelated session.
2. Follow child-sessions' foreground loop: `wait <name> <status-file> 240` on Codex, `540` on Claude. A Codex tool yield is not timeout: poll the same returned foreground session in intervals at most 60 seconds until it exits. Repeated fresh 20-second waits reset silent-exit grace and are invalid.
3. On exit `0`, read the exact first status line. `done` proceeds to Verify; `blocked` shows Questions/options/recommendation, obtains the user's answer, archives to `<file>-blocked-<n>`, sends one line or an absolute answer-file instruction, then waits for fresh status. `failed` shows the failure and stops, preserving window/worktree/status; nothing is written to follow-ups.
4. Exit `3`: `peek <name> 40`, show diagnostics, append “Continue from the current state of the checkout: read git log and run the checkout-state preflight first.” to the retained brief, close the stale window if present and reopen once with the same options. Second silent exit stops. Exit `124`: `peek <name> 40`; wait again for work in progress, or handle a dialog per child-sessions Dialogs. Other errors stop with artifacts preserved.

## Verify

1. Require the full owned status format. Match BRANCH/CHECKOUT/HEAD to the registered task worktree, its current branch and full HEAD; validate recorded base ancestry. Require a clean preflight and exact `git log --oneline <base>..<branch>` agreement with Commits. Take the reviewed HEAD from `Reviewed HEAD:` under Review; it must be on the branch. After it the branch may hold only commits with the subject `follow-ups: <branch>` whose changed paths (`git diff --no-renames --name-only -z <commit>^ <commit>`, NUL-separated) are exactly the follow-ups file, and only in the tracked layout; in the separate-docs and ignored layouts the reviewed HEAD is HEAD. Any mismatch stops integration; return it to the child for a fresh report, preserving evidence.
2. Read Checks, Review and Out of scope. Require successful required checks and final refine mode `CLEAN` or `CLEAN EXCEPT DISPUTED`. Preserve the separate raw reviewer verdict: dispute-only closure can retain raw `CHANGES` under review-fix-loop; never relabel it CLEAN. Missing completion evidence goes back to the child, without root re-review.
3. For `CLEAN EXCEPT DISPUTED`, show disputed findings and both positions; ask the user whether to accept the branch as ready to merge, return to the child, or stop. Accept it only after that decision; retain all deferred/outside-scope findings for follow-ups.

## End

Runs only after Verify passed and, for `CLEAN EXCEPT DISPUTED`, the user accepted the branch.

1. Gather the follow-ups from the verified status: Out of scope plus the deferred minor, outside-scope and disputed review findings, one line each as `- <what> — <where> — <why>`. The follow-ups file is `<document-stem>-follow-ups.md` beside the task document.
2. Tracked: on the task branch, the file's `## <branch> @ <reviewed-sha7> (<date>)` section must list exactly the gathered findings, its `<reviewed-sha7>` matching the reviewed HEAD; with no findings the branch has no section there. A mismatch goes back to the child for a fresh report, as Verify 1 does. Main stays untouched: the file reaches main only with the branch.
3. Separate docs: perform the root's installed `writing-task-follow-ups` with `--doc <task document in the docs main checkout> --branch <branch> --head <reviewed HEAD> --checkout <docs main checkout>` and the gathered findings. Ignored: perform it with `--doc <task document> --branch <branch> --head <reviewed HEAD> --checkout <main checkout> --no-commit`.
4. Report branch, worktree, commits, final refine mode and raw reviewer verdict, follow-ups path and count, and the follow-ups commit (on the task branch or in the docs repository) or where it was written locally. Window, worktree and branch stay: the window answers a main-moved return before a merge. This skill merges nothing and cleans nothing up.
