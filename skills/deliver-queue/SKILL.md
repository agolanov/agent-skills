# Deliver Queue

`deliver-queue <queue-file> [--parallel N] [--agent claude|codex] [--model M] [--effort E]`
`deliver-queue <plan>... [--parallel N] [--agent claude|codex] [--model M] [--effort E]`

The root writes no code. Per-unit work is `deliver-task`'s sections, read from its installed SKILL.md at run time and performed exactly as written, with this queue's `--agent/--model/--effort` passed to every unit. Every brief and message a child receives (implementer brief, main-moved authorization, continuation line, answers) is `deliver-task`'s or `child-sessions`' exact text, never a paraphrase. This skill only decides when each unit starts, waits and merges, and records states. `--parallel N` (default 3) bounds live windows (Scheduling 3).

## Input

1. Queue file: rows give unit, order `#`, `Depends on`, plan, spec and `State` (format and state vocabulary: `prepare-tasks/references/queue-file.md`). Plain list: one unit per plan, named by its full stem (`2026-10-29-alpha`), spec `<plan-stem>-design.md` beside it, each depending on the previous plan unless the user says they are independent. In both forms branch and window are exactly what `deliver-task` Preflight 2 derives from the plan: no `--branch` override, no shortened names.
2. Normalize states: `delivered <sha7>` is done; `not ready: <reason>` is skipped and reported; every other state is a candidate again, its dependencies re-evaluated against delivered units. A plain list takes states from an earlier run's state file only when its header lists the same absolute plans in the same order (state-file.md), else every unit is `ready`.
3. Already merged: after Preflight 1–3 and before step 4's question, for each candidate take `<branch>` as step 1 says and search the first-parent history of the project main checkout's main branch (`git log --first-parent --merges --format='%H%x09%cs%x09%s' <main>`, merge commits only) for a subject equal, as a whole fixed string, to `Merge branch '<branch>'` or `Merge branch '<branch>' into <main>`; the most recent match counts. For each found unit show the merge's short SHA and date and ask once: record it `delivered <sha7>` (recommended), or deliver it again. A recorded unit counts as delivered for dependencies and is no longer a candidate, so steps 4–6 never touch it. List its leftovers without acting on them: a worktree or branch under its name (Cleanup not done), a live window with its name (`child-session list`), a missing `<runtime>/<branch>-tails-brief.md` (Tails not recorded); finishing them is the user's call. Such a live window is a retained window under Scheduling 3: it counts toward `--parallel` while `alive` returns 0, but not for overlap (Scheduling 2), since its changes are already on main. A unit to deliver again stays a candidate; if step 6 then finds its leftovers, it recommends discard, since that branch is already on main. No match, no question.
4. Before any batch point or window, list the candidates with a `not ready` dependency and ask the user once, for each: run it as independent (drop that dependency), or skip it as `not started: depends on not ready <unit>`; units depending on a skipped one get the same state. The user decides; never choose for them.
5. Once Preflight 1–3 are done (before Preflight 4), for each candidate whose branch, worktree (`git worktree list`) or window (`child-session list`) exists under the names `deliver-task` derives, prove ownership as `deliver-task --resume` does: `<runtime>/<branch>-brief.md` (`<runtime>` = `${XDG_RUNTIME_DIR:-/tmp}/child-sessions`) exists and names this plan and spec; its Branch and Checkout match the registered worktree and branch; a live window with its recorded name lists the brief's checkout. No window is normal after a failure. A candidate with only an old brief or status and no branch, worktree or window is proven only when the brief names this plan and spec and its Checkout is the path `deliver-task` Worktree 1 derives for this branch in this project (no brief: the status's CHECKOUT must be that path); runtime names are shared by every project, so anything else is another task's artifact. A missing brief where a branch, worktree or window exists, or any mismatch, stops the whole run before any batch point or window: report it, close, delete and rename nothing (`close` and `git branch -D` act by name); the user resolves it and reruns.
6. Only then show each proven unit's leftovers and last status and ask once per unit: resume through `deliver-task --resume` (recommended when the status reported commits), or discard: `close` the window if live, `git worktree remove --force <path>`, `git branch -D <branch>`, archive the old brief and status, then start fresh. A proven candidate with only an old brief or status cannot resume: show each file's path and the status's first line and Commits, or `no status file`, then archive them without a question. To archive, rename a file to its full name plus `-old-<n>`, `n` the smallest number whose name is unused (`2026-10-29-beta-status.md` → `2026-10-29-beta-status.md-old-1`), never replacing an existing file.

## Preflight

1. Project main checkout (the queue's `Project checkout:`, else the top level of the current repository as `prepare-tasks` Preflight 1 resolves it; when that is a separate docs repository rather than the project, ask the user for the project checkout) on its main branch with empty `git status --short`. Docs repository by `prepare-tasks` Preflight 2; both layouts are allowed (documents tracked by the project, or a separate docs repository). A queue file must live in it and match its `Docs repository:` line. Require docs main on its main branch and clean.
2. Locate the installed `deliver-task/SKILL.md` and its references, `child-sessions/SKILL.md` with its references and `scripts/child-session` (absolute path, never PATH), and `prepare-tasks`; read them completely.
3. Select the agent as `deliver-task` Preflight 2 does. Run `deliver-task` Preflight 3–4 (child-sessions and the child's dependency check) once for that agent; missing dependencies stop before anything opens.
4. Create the runtime state file per [state-file.md](references/state-file.md) with every unit and its normalized state.

## Scheduling

Runs at the start, at the end of each drain that merged (Finish half 2), and whenever a slot frees while no batch point (b) is pending.

1. Startable: a candidate not yet started whose dependencies are all `delivered`.
2. Read [overlap.md](references/overlap.md). Hold back a startable unit that overlaps a unit with a live window or an earlier unit chosen in the same pass; it waits until that window is gone, normally after its merge.
3. Live windows: `running`, `blocked`, `rebasing` and `done awaiting merge` (its agent stays alive for a possible main-moved return until Cleanup), plus a `failed` window until `close` and `alive` returning 1, and a delivered unit's window whose Cleanup `close` failed or a unit recorded by Input 3 whose window was left alive, while `alive` (rechecked at each Scheduling) returns 0. Choose startable units in queue order until live windows reach `--parallel`. If such retained windows (failed, stopped or delivered, their `close` failed and `alive` still 0, or recorded by Input 3 and left alive) keep a startable unit waiting while no unit is working or awaiting merge, report them and ask the user: they close the window (recheck `alive`, then Scheduling again; a failed or stopped unit keeps its worktree, branch and status file), or the run goes to End with the waiting units `ready`.
4. Mark the chosen units `running` in the state file. At the start and at the end of a drain that merged, the batch point comes next; after a freed slot, go straight to the start half.

## Start half

For each chosen unit in queue order, perform `deliver-task` Preflight 1–2, Worktree, Brief and Open and wait 1 (open), exactly as written; a resumed unit takes its `--resume` path. The Wait loop below replaces Open and wait 2. Record branch, window, status file and base SHA in the state file. A stop inside the start half makes the unit `failed: <reason>` (Wait loop 4).

## Batch point

Write the queue file's `State` column from the state file and commit `queue: <slug> progress` per state-file.md, only: (a) after the first scheduling, before any worktree is created; (b) at the end of a drain (Finish half 2), after its last merge's Tails and Cleanup and the next scheduling, before any new worktree (one commit records every merge of the drain); (c) at End. A failure, a block, a Verify return or a failed rebase is never a batch point. Because (a) and every (b) precede the next Worktree step, each new child starts from a main that already holds the queue commit: with documents tracked by the project, no child is ever moved past by a documentation-only commit.

## Wait loop

1. Round-robin over windows whose agent is working (`running`, `rebasing`, a `blocked` window after its answer): one foreground `wait <name> <status-file> 150` per window per turn, then the next window, with the host's command timeout set above the wait (180 s or more) so the host can never move it to the background; a wait still running beside other commands is not the loop. Never 120 or less, never several waits in one shell call or in the background, never one long wait on a single window. A Codex tool yield is not a timeout: poll the same command as child-sessions says. `done awaiting merge` windows are not waited on again.
2. Exit 0: read the first status line of every working window. Each `done` of a `running` unit becomes `done awaiting merge`; a `rebasing` unit keeps its state until its finish half ends. Then go to Finish half, or back to the loop when the hold allows none.
3. `blocked`: state `blocked: <question>`; answer it per `deliver-task` Open and wait 3; back to its previous state (`running` or `rebasing`). A hold set on the unit persists throughout. Other windows keep going.
4. `failed`, unlike `deliver-task`'s stop, because an interactive agent stays alive after writing `failed` and would hold a slot: state `failed: <reason>` in the state file only, `peek <name> 40` for the report, `close <name>`, free the slot only once `alive <name>` returns 1 (a failed `close` is Scheduling 3's retained window). Keep worktree, branch and status file. Its dependents, transitively, become `not started: depends on failed <unit>`; other units continue. Run Scheduling unless batch point (b) is pending (the drain's end runs it), then drain (Finish half 2). A unit the user stops is `stopped by the user`, handled the same way, except that its dependents, transitively, become `not started: depends on stopped <unit>`.
5. Exit 124: next window; `peek` now and then for a dialog, answer within authority or ask the user. Exit 3: `deliver-task` Open and wait 4's single reopen; a second silent exit or any other error counts as `failed`.

## Finish half

1. One finish half at a time. Pick, among `done awaiting merge` units, the one whose status file has the earliest modification time, not the window whose wait returned. The hold: from a main-moved return (step 4) until that unit is `delivered`, `failed` or `stopped by the user`, through any block or Verify return, the only finish half allowed is that unit's, once its fresh status says `done`.
2. Drain: whenever a finish half is allowed (after a Wait loop exit 0, a delivery, a failure or stop, a Verify return), run it at once; the Wait loop runs only while none is allowed. A merge leaves batch point (b) pending (step 6). With none pending, a drain has no end step: when no finish half is allowed, go back to the Wait loop. While it is pending, a held unit's rebase belongs to the drain: the drain ends when no finish half is allowed and the hold is not set. Then run Scheduling, batch point (b), which clears the pending mark, and the start halves, then go back to the Wait loop.
3. Perform `deliver-task` Verify, Merge, Tails and Cleanup exactly as written; the merge keeps Git's default message (no `-m`), which Input 3 relies on.
4. Merge returns the child for main-moved: state `rebasing`, base SHA updated as `deliver-task` records it, back to the Wait loop with the hold set. Fresh `done`: this unit resumes at Verify. `failed`: Wait loop 4, which releases the hold with no batch point; drain.
5. Verify or a disputed-findings decision returns the unit to its child: a `rebasing` unit stays `rebasing` and keeps the hold, any other becomes `running` (nothing merged, no hold); drain.
6. Merged and cleaned up: `delivered <sha7>` with tails count and follow-up brief path (a Cleanup failure is reported; the unit is still delivered, and a window left alive keeps its slot per Scheduling 3); batch point (b) is now pending. Read the first status line of every working window as Wait loop 2 does, then drain (step 2).
7. A stop before the merge commit is `failed: <reason>` (conflict) or `stopped by the user`, both per Wait loop 4. A stop after it (tree inequality, failed required post-merge check) leaves main suspect: record `failed: <reason>`, start and merge nothing more, go to End leaving other windows as they are.

## End

When no window is working or awaiting merge and nothing is startable: batch point (c), then report a table `unit | state | merge SHA | tails count | follow-up brief path`, then every unit never started with its reason, and the kept worktree, branch and status file of each failed unit, and the leftovers listed for each unit recorded by Input 3.
