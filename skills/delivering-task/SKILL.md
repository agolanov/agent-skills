# Delivering Task

For each clean/path gate and continuation below and in child briefs, use the four ordinary Git commands and identity checks in [checkout state](../independent-review/references/checkout-state.md#direct-use-preflight), with process-local `GIT_OPTIONAL_LOCKS=0`, actual exits and raw output files. A clean gate requires successful commands and empty status and diffs; path gates parse NUL-delimited status and compare exact repository-relative paths, including both rename paths. Failed or unavailable Git evidence stops the dependent action. Use ordinary Git for other read-only checks, retaining real exits. Evidence has the reference's ignored/untracked-content, Git flags/normalization, nested-repository and transient-write limits. Stage/commit only owned paths; write, merge and push authority stays explicit.


`delivering-task <document | directory>... [--no-merge] [--parallel N] [--independent] [--run window|inline|subagent|background] [--agent claude|codex] [--execution inline|subagents|direct] [--model M|cli-default] [--effort E|cli-default] [--reviewer-run background|subagent|window] [--reviewer-model M|cli-default] [--reviewer-effort E|cli-default] [--spec S] [--branch B] [--resume] [--auto]`

One document: Execute (the sections Preflight through End below), then Merge and Cleanup. A refusal, a stop or a `failed` status in Execute ends the run with nothing merged. With `--no-merge` the run stops after End with a ready branch and reports it. Several documents or a directory: read [queue.md](references/queue.md) and follow it; its per-unit work is the sections below. The queue text is read only in this case. `--spec`, `--branch` and `--resume` take one document only: given with several documents or a directory, they stop the run before anything starts, naming the key; the queue finds leftovers itself. `--parallel` and `--independent` apply to several documents: `--independent` (no unit depends on another, replacing the queue's dependency inference) given with one document stops the run before anything starts, naming the key.

The child owns implementation, refinement and, in the tracked layout, its follow-ups commit. The root checks Git/status facts, records follow-ups the child cannot commit and integrates; it does not write product code, add commits to the task branch, or repeat the child's tests or review. Follow-ups are written only through [follow-ups.md](references/follow-ups.md), by the child in the tracked layout or by End 3; in the tracked layout Merge carries them to main with the branch.

## Preflight

1. Resolve the main checkout, main branch, the absolute task document path, and applicable project rules. Require the main checkout on its main branch; uncommitted changes are allowed and stay untouched. The check still takes a four-command boundary, and failed Git evidence stops. Recognise the document and read it completely:
   - **Plan**: it carries the superpowers plan header (`> **For agentic workers:** REQUIRED SUB-SKILL:`) or lies in a `plans/` directory of a superpowers docs dir (`docs/superpowers/plans/`) and is not a `*-follow-ups.md` or `*-tails.md` file. Spec: `--spec`; else `<plan-stem>-design.md` beside the plan or in the sibling `specs/` directory; else the plan's `**Spec:**` header (path relative to the project checkout); else `None`, with no question.
   - **Spec**: named `*-design.md` or lying in a `specs/` directory. Find its plans in the sibling `plans/` directory by the matching rules: the naming pair (`specs/YYYY-MM-DD-<slug>-design.md` with `plans/YYYY-MM-DD-<slug>.md`), then every plan whose `**Spec:**` header names this spec. None: refuse before any worktree or window, telling the user to write the plan with `planning-task-docs`. One: that plan is the task document, this spec its spec. Several: list them and ask the user which one to execute.
   - **Other**: any other file is a task document implemented directly (a brief, a task text). Spec `None`.

   `--spec` is accepted only with a plan. Layout: the docs repository is `git -C <document-dir> rev-parse --show-toplevel`, named by its main-checkout absolute path. **Tracked**: it is the project and `git -C <main-checkout> check-ignore -q <document-dir>` exits non-zero. **Separate docs**: it is another repository (nested in an ignored directory or elsewhere); require its main checkout on its main branch the same way, uncommitted changes allowed and untouched. **Ignored**: it is the project and that `check-ignore` exits 0 (ignored without its own repository). Show the user the document's kind, its spec and the layout, and the review-mark state of the task document and its spec per [review-mark.md](references/review-mark.md): fresh with verdict, reviewer and date; else `none` or `stale` with the failing freshness condition. The mark state is information only; continue whatever it is.
2. Decide the execution mode per [Execution mode](#execution-mode). `--execution` is an explicit mode; a value invalid for the document kind (`subagents` for another document, `direct` for a plan) stops before any worktree or window, naming the value and the kind. A caller that decided the mode by that section's rule (as the queue does for its units) passes it labelled as caller-decided: record it with source `rule` without deciding again; it is not an explicit override. A mode the user gave the caller explicitly is passed as an explicit `--execution`. Show the mode, its source, its reason and, for `inline`, the effort with its reason beside Preflight 1's display, as information; the run continues without a question. Select `--agent`, otherwise identify the root's own system from session identity as independent-review's [Session system](../independent-review/SKILL.md#session-system) does; unknown identity requires clarification. For `--resume`, recover recorded launch identity, its `Execution mode:` line included, subject to the provenance checks below; conflicting explicit overrides stop. Except on `--resume`, resolve the implementer's settings per [launch settings](../independent-review/references/launch-settings.md#precedence) for the selected agent: `--model`/`--effort` are explicit values, `cli-default` is a per-field [opt-out](../independent-review/references/launch-settings.md#cli-defaults-opt-out), and every other field takes the default of the mode's role per [launch settings](../independent-review/references/launch-settings.md#roles): `inline implementer` for `inline`, with the effort of the inline effort rule; `implementer` for `subagents` and `direct`. So `--model cli-default` in `inline` mode omits only the model; the effort is still the rule's `medium` or `high`, passed explicitly. A caller that resolved values from the policy (as the queue does for its units) passes them labelled as policy values: record them with source `policy` without re-resolving; they are not explicit overrides. An unresolved or unsupported pair stops before any worktree or window. Validate explicit `--reviewer-model`/`--reviewer-effort` values for the reviewer system the place resolves, the child's own system under `--reviewer-run subagent`, otherwise the system opposite to the child's agent: a model of another system or an unsupported pair stops before any worktree or window, naming the value and the reviewer system; `cli-default` is accepted. These values fill the brief's Reviewer settings line; without them it says `reviewer policy`. `--reviewer-run <place>` fills the brief's Reviewer run line as `<place> (explicit)`; without it the line says `background (default)`. A place other than `background`, `subagent` or `window` stops before any worktree or window. Never infer the agent from executable availability, environment, directory names, or model. Default branch to the task document's stem (the plan's stem for a plan or a spec resolved to its plan); validate with `git check-ref-format --branch`, asking for a valid override if invalid. Use window `<name> = impl-<branch>` for `[A-Za-z0-9_-]+` branches; otherwise replace disallowed branch characters with `-` and use `impl-<slug>-<hash8>` (first eight SHA-256 hex characters of the full branch name). Record the unique name; never alias slash/dot branches by slug alone.
3. Locate root's installed `child-sessions/SKILL.md`; read it and its owned `references/brief-writing.md` and `references/status-file.md`. Resolve its installed platform entrypoint by absolute path (Bash `scripts/child-session`; native Windows `scripts/child-session.ps1` through the installed PowerShell vector in its platform reference). Its command/status contract governs every call below. Set `<runtime>` from successful `runtime-dir` output, outside Git.
4. Check the selected child's actual installed catalog/directories: Claude's `~/.claude/skills`, enabled `~/.claude/plugins`; Codex's `~/.codex/skills`, `~/.agents/skills`, enabled `~/.codex/plugins`; plus project `.claude/skills` and `.agents/skills` available to that child. Resolve readable absolute paths for `review-fix-loop`, `independent-review`, `child-sessions` when the Reviewer run place is `window` (the child opens that reviewer window itself), and, for a plan, the execution skill its mode names (`executing-plans` for `inline`, `subagent-driven-development` for `subagents`): a missing one stops before opening and is never replaced by the other. Another document needs no execution skill. Follow-ups writing is this skill's [follow-ups.md](references/follow-ups.md), never a separate skill: the child in the tracked layout and End 3 use this skill's installed copy. Verify checkout-local paths remain available in the worktree. Executables or the root's catalog alone do not prove child skill availability. Missing dependencies stop before opening; report them for the user to install, without substitution.

## Execution mode

Preflight 2 decides one execution mode per run, after Preflight 1 has read the task document and before any settings are resolved. The mode names the child's execution skill and its [launch settings role](../independent-review/references/launch-settings.md#roles):

| Mode | Task document | Brief's Execution line | Role |
| --- | --- | --- | --- |
| `inline` | plan | `executing-plans` | inline implementer |
| `inline` | other | `None: direct implementation` | inline implementer |
| `subagents` | plan | `subagent-driven-development` | implementer |
| `direct` | other | `None: direct implementation` | implementer |

`subagents` is valid only for a plan, `direct` only for another document, `inline` for both.

1. **Given mode.** An explicit `--execution` valid for the kind, a caller-decided mode (source `rule`) and, on `--resume`, the mode the brief records (Worktree 3) are taken as given. An explicit `--execution inline` on a large document is honoured, with no warning or question. The rule in step 2 runs only when none of these applies.
2. **Rule.** Read these signals from the document:
   - **Count and size** of the tasks (a plan) or of the separate changes (another document): how many, how many files each touches, how long each is.
   - **Kind of steps:** mechanical (the exact code or text to write is in the document) or prose (the implementer must design how).
   - **Overhead:** `subagent-driven-development` dispatches an implementer and reviewers for every task. When that per-task dispatch and review is comparable to the task's own work (a few line edits, one short file), it is overhead.

   A plan is `inline` when it has few tasks, each small, and the per-task overhead is comparable to the work; `subagents` when it has many tasks or any large one. Dependencies between tasks (one builds on another, tasks edit the same file) are not a reason for `inline`: `subagent-driven-development` runs tasks one at a time. Another document is `inline` when it asks for a few small, localized changes; `direct` otherwise. When the signals disagree or the size is unclear, choose `subagents` for a plan and `direct` for another document: a wrong large mode costs tokens, a wrong small mode can ship a mistake.
3. **Inline effort.** Whenever the final mode is `inline`, whatever its source, and the effort has no explicit flag (`cli-default` included), recorded value or caller-resolved policy value: `medium` when the steps are mechanical (the document carries the complete code or text); `high` when any step is prose and the implementer decides how to implement it. A given mode skips step 2, never this step.
4. **Output.** The mode; its source, `rule` (decided here or by the caller) or `explicit`; a one-sentence reason naming the signals that decided it; and, for `inline`, the effort with its reason. The brief records them as `Execution mode: <inline | subagents | direct> (<rule | explicit>); <reason, one sentence>`.

## Worktree

1. Use the project worktree convention, otherwise `<main-checkout>/.worktrees/<branch>`. Resolve the main checkout and selected path, including existing symlinks. For a path inside the main checkout, run `git check-ignore`; if it is not ignored, tell the user and stop without changing ignore rules. For an external path, apply the same ownership/existence checks without an ignore prerequisite. Refuse any existing branch or worktree, naming both, unless `--resume`.
2. For a new task (a `--resume` commits nothing), first commit its documents, the paths this step owns: in the tracked and separate-docs layouts, the task document and then its spec when not `None`, each alone in the repository holding it, `<repo>` = `git -C <document-dir> rev-parse --show-toplevel`. For each document take a fresh four-command boundary of `<repo>`; failed Git evidence stops, as at every gate. The document has uncommitted changes (untracked, staged or unstaged alike) when its exact repository-relative path `<rel>` equals a path of the NUL-delimited status, either path of a rename or copy entry included. With changes run `git -C '<repo>' --literal-pathspecs add -- '<rel>'`, then `git -C '<repo>' --literal-pathspecs commit -m 'docs: <basename>' -- '<rel>'`, and show `committed <rel> <sha7>`; without changes commit nothing. Each path and message is one literal shell argument, quoted for the shell that runs it (inside POSIX single quotes a single quote is written `'\''`; inside PowerShell single quotes it is doubled), and `--literal-pathspecs` keeps Git from reading a file name as pathspec magic. The pathspec commits the document alone: other staged changes stay staged, unstaged and untracked paths stay as they are, and when the document is one side of a staged rename only its own path is committed, the other side staying as it is. A failing `add` or `commit` stops before any worktree or window, reporting Git's error. The ignored layout commits nothing and shows no commit line, its documents never being committed; the count lines that follow still apply. Then show `unrelated uncommitted changes left untouched: <count>` for the main checkout and, in the separate-docs layout, `<docs main checkout>: unrelated uncommitted changes left untouched: <count>` for the docs repository. The count is the number of distinct paths in the status of that repository's last boundary (this step's, else Preflight 1's), both rename or copy paths counted, other than a document committed here; the paths are never listed, and a count of 0 shows no line. The commits and counts are information; the run continues without a question. Then record full main HEAD as `<base-sha>` and run `git worktree add -b <branch> <path> <base-sha>`; in the tracked layout that base includes the document commits, so the worktree holds the documents. Verify its branch and HEAD match. Keep runtime files under the helper's `<runtime>` outside Git, creating parent directories for nested branch names.
3. For `--resume`, require the prior runtime brief whose identity block carries `Written by: delivering-task`. Any other brief stops before reopening, naming it: “brief written by a removed skill; finish that run with the catalog that started it, or remove its branch, worktree and runtime files by hand”. Require in it base, absolute task document/spec identity, branch, checkout, window name and its `Execution mode:`, `Launch settings:`, `Reviewer settings:` and `Reviewer run:` lines. Match it to the requested task and registered Git worktree/branch; validate the recorded base exists and belongs to the task history. Reuse the recorded base/window identity, never today's main as a guessed replacement, and the recorded settings and `Reviewer run:` place, never re-resolved: an explicit flag equal to the recorded value is accepted, a different one stops; caller-resolved policy values never conflict, the recorded values win. The recorded `Execution mode:` line is reused the same way, never decided again: an explicit `--execution` equal to it is accepted, a different one stops; a caller-decided mode never conflicts, the recorded mode wins. Missing, conflicting or ambiguous provenance stops. Preserve current work for the child, archive any prior status to an unused suffix. Then append “Continue from the current state of the checkout: read git log and record the ordinary Git evidence and verify checkout/branch/HEAD first.” An old terminal report cannot complete a resumed run.

## Brief

1. Read [implementer-brief.md](references/implementer-brief.md), fill every placeholder, and write `<runtime>/<branch>-brief.md`; status is `<runtime>/<branch>-status.md`. Persist task identity/base and the `Written by:`, `Execution mode:`, Launch settings, Reviewer settings and Reviewer run lines for resume. Resolve required skill paths for the child's actual checkout/catalog, and provide the absolute owned status-contract path. Fill Layout facts: docs repository as Preflight 1 found it, named by its main-checkout absolute path even when it is the project itself; Follow-ups in the tracked layout is the absolute `<document-stem>-follow-ups.md` path beside the task document inside the worktree plus the absolute path of this skill's installed [follow-ups.md](references/follow-ups.md), otherwise `the root records them`; ignored test material is the test path the project rules state, else `tests/`, resolved against the main checkout to an absolute path; use it when it exists and `git -C <main-checkout> check-ignore -q <path>` exits 0, otherwise `None`. A stated path that fails either check is `None`, never replaced by `tests/`; before opening, tell the user which path failed which check. Follow child-sessions' self-contained brief checklist.
2. Keep the exact `Status file: <status-file>` line. A new task requires an absent status path; an existing artifact needs provenance validation or a stop, not silent reuse. Only the child writes status contents.

The brief's `Terminal controls:` line is the template's fixed text: the brief is written before `open`, when no launch exists to report a backend or controls. After every `open` (the first, a reopen, a resume), read that launch's `capabilities <name>` and check its checkout/launch identity before any terminal control; every `peek`, `send` and `key` below is conditional on the current launch's supported capability, never on the brief, and nothing about controls is written into the brief or sent to the child. When the current launch's record lacks `peek`, `send` or `key`, tell the user once for that launch that questions/dialogs need direct attention in that window, then continue through brief/status files; report dialog counts as not observable. A known `blocked` question still follows the status contract, with its answer entered directly by the user when `send` is unavailable. A timeout alone supplies no question or approval. Check `alive` before any supported input; never reopen a live agent to inject text. Reopen a proven dead launch at most once under the shared budget below. `close` stops only proven owned processes; unavailable window closure leaves a reported retained window, whose shell alone is not a live agent.

## Open and wait

1. Append the `Opened:` line of the [child settings check](../independent-review/references/launch-settings.md#child-settings-check) to the brief, then call the resolved script: `open --agent <agent> [--model M] [--effort E] <name> <path> <brief>`, quoting paths, passing the brief's recorded Launch settings as `--model` and `--effort` and omitting a field that is `cli-default`. On explicit resume reuse the recorded window, the recorded Launch settings and the continuation brief, with a new `Opened:` line; close any owned stale window before reopening, never an unrelated session.
2. Follow child-sessions' foreground loop: `wait <name> <status-file> 240` on Codex, `540` on Claude. A Codex tool yield is not timeout: poll the same returned foreground session in intervals at most 60 seconds until it exits. Repeated fresh 20-second waits reset silent-exit grace and are invalid. At the first `wait` return after each `open`, run the early [child settings check](../independent-review/references/launch-settings.md#child-settings-check) for that opening and keep the matched record path; only a mismatch stops the loop for the user's continue-or-stop question.
3. On exit `0`, read the exact first status line. `done` proceeds to Verify; `blocked` shows Questions/options/recommendation, obtains the user's answer, archives to `<file>-blocked-<n>`, puts the answer in one line or an absolute answer-file instruction, then sends it per step 5 and waits for fresh status. `failed` shows the failure and stops, preserving window/worktree/status; nothing is written to follow-ups.
4. Exit `3`: `peek <name> 40`, show diagnostics, append “Continue from the current state of the checkout: read git log and record the ordinary Git evidence and verify checkout/branch/HEAD first.” to the retained brief, close the stale window if present, append a new `Opened:` line and reopen once with the brief's recorded Launch settings; never re-resolve them. Second silent exit stops. Exit `124`: `peek <name> 40`; wait again for work in progress, or handle a dialog per child-sessions Dialogs. Other errors stop with artifacts preserved.
5. Before every `send` (a `blocked` answer in step 3, a return to the child in Verify 1–3 or End 2), make sure the status file is archived to an unused suffix (step 3's `<file>-blocked-<n>`; `<file>-returned-<n>` for a Verify or End return), so that step 2's wait returns only a fresh status; then run `alive <name>`: a dead agent leaves a shell that would run the text. Dead: `close <name>`, append the continuation line of step 4 and then the line you meant to send to the retained brief, append a new `Opened:` line, `open` again with the brief's recorded Launch settings, never re-resolved, and wait per step 2; this is the run's one reopen, shared with step 4. When that reopen was already used, stop and report, keeping the window, worktree and runtime files.

## Verify

1. Require the full owned status format. Match BRANCH/CHECKOUT/HEAD to the registered task worktree, its current branch and full HEAD; validate recorded base ancestry. Require a clean preflight and exact `git log --oneline <base>..<branch>` agreement with Commits. Take the reviewed HEAD from `Reviewed HEAD:` under Review; it must be on the branch. After it the branch may hold only commits with the subject `follow-ups: <branch>` whose changed paths (`git diff --no-renames --name-only -z <commit>^ <commit>`, NUL-separated) are exactly the follow-ups file, and only in the tracked layout; in the separate-docs and ignored layouts the reviewed HEAD is HEAD. Any mismatch stops integration; return it to the child per Open and wait 5 for a fresh report, preserving evidence.

   Then run the final [child settings check](../independent-review/references/launch-settings.md#child-settings-check) over every opening's record of the run. A settings mismatch or `settings unverified: <reason>` never returns to the child: show expected and observed values and the record paths, and ask the user to accept the result with the observed settings (recorded as accepted for the report) or stop, preserving window, worktree and status.
2. Read Checks, Review and Out of scope. Require successful required checks and final refine mode `CLEAN` or `CLEAN EXCEPT DISPUTED`. Preserve the separate raw reviewer verdict: dispute-only closure can retain raw `CHANGES` under review-fix-loop; never relabel it CLEAN. Missing completion evidence goes back to the child per Open and wait 5, without root re-review.
3. For `CLEAN EXCEPT DISPUTED`, show disputed findings and both positions; ask the user whether to accept the branch as ready to merge, return to the child per Open and wait 5, or stop. Accept it only after that decision; retain all deferred/outside-scope findings for follow-ups.

## End

Runs only after Verify passed and, for `CLEAN EXCEPT DISPUTED`, the user accepted the branch.

1. Gather the follow-ups from the verified status: Out of scope plus the deferred minor, outside-scope and disputed review findings, one line each as `- <what> — <where> — <why>`. The follow-ups file is `<document-stem>-follow-ups.md` beside the task document.
2. Tracked: on the task branch, the file's `## <branch> @ <reviewed-sha7> (<date>)` section must list exactly the gathered findings, its `<reviewed-sha7>` matching the reviewed HEAD; with no findings the branch has no section there. A mismatch goes back to the child per Open and wait 5 for a fresh report, as Verify 1 does. Main stays untouched: the file reaches main only with the branch.
3. Separate docs: perform Write follow-ups of [follow-ups.md](references/follow-ups.md) with `--doc <task document in the docs main checkout> --branch <branch> --head <reviewed HEAD> --checkout <docs main checkout>` and the gathered findings. Ignored: perform it with `--doc <task document> --branch <branch> --head <reviewed HEAD> --checkout <main checkout> --no-commit`.
4. Report branch, worktree, commits, final refine mode and raw reviewer verdict, one execution mode line (mode, its source `rule` or `explicit`, and reason), one implementer settings line (role `inline implementer` or `implementer` by the mode; effective model and effort, source of each, the settings check outcome per opening, and the record paths or the user's acceptance), the brief's Reviewer settings and Reviewer run lines, Worktree 2's count lines when it showed any, follow-ups path and count, and the follow-ups commit (on the task branch or in the docs repository) or where it was written locally. Window, worktree and branch stay: the window answers a main-moved return before a merge. End merges nothing and cleans nothing up: Merge and Cleanup follow, except under `--no-merge`. There, with one document, this report ends the run and names the ready branch, saying nothing was merged; inside the queue, its Finish half continues.

## Merge

1. Immediately before merging, require main still on its branch, and compare full main HEAD to recorded base. If changed, archive status, retain the prior brief and append the new target plus this one-time authorization: “main moved to <sha>: rebase onto it, rerun the checks and one fix-review round, write a new status”. Tell the child to use `<sha>` as its reporting/review base. Send that sentence word for word, with `<sha>` filled in, to the same child through Open and wait 5: a dead child gets that step's reopen with the authorization as the line to send, counted against the same run. Then wait, verify a fresh report against that target, then update the recorded Base SHA in the runtime brief. Perform Verify and End again, then repeat this latest-main check; no stale status or merge before refresh.
2. With main HEAD at the recorded base `<base>`, run the dirty-path gate immediately before `git merge`: take a fresh four-command boundary of the main checkout `<main>`; failed Git evidence stops, as at every gate, and a HEAD other than `<base>` means main moved: return to Merge 1. Staged changes (a non-empty cached diff, or a status entry whose first column is neither a space nor `?`) stop, naming the staged paths: Git refuses a non-fast-forward merge while the index differs from HEAD, even for unrelated paths. Otherwise list the branch's paths with `git -C <main> diff --no-renames --name-only -z <base> <branch>` and the paths it adds with the same command plus `--diff-filter=A`, both NUL-separated and never word-split. A branch path intersects when it equals a status path, either rename or copy path included; when it or one of its leading directories (`a` and `a/b` for `a/b/c`) is reported ignored and exists as anything but a directory; or when the branch adds it and it exists as a directory holding untracked content, ignored files included: `git -C <main> --literal-pathspecs ls-files -z --others -- <path>`, the path one literal argument, prints an entry (files tracked there are the branch's own deletions and pass; a nonzero exit is unavailable evidence and stops). Git overwrites or deletes such ignored content silently and refuses only for untracked content that is not ignored. For the ignored test take the branch paths and their leading directories, leave out every path below a leading directory that exists in the main working tree as anything but a directory (Git does not look beyond a symlink; that leading path is judged alone), and feed the rest, each written as `./<path>` (a name beginning with `:` would otherwise be read as pathspec magic and fail the command), NUL-separated, as standard input to `git -C <main> check-ignore -z --stdin` (exit 0: it prints the ignored ones as given, NUL-separated, and their leading `./` is dropped before comparing; 1: none is ignored; any other exit is unavailable evidence and stops). Judge existence and directories in the main working tree by lstat: a dangling symlink exists and a symlink is never a directory (on POSIX `test -e || test -L`, and `test -d` only with `! test -L`). Intersections stop, naming the main working tree paths in the way. A staged or intersecting stop is reported as `dirty main: <paths>` and keeps window, worktree, branch and status; nothing is stashed, unstaged, restored or committed. With one document the run ends there; the queue holds the unit instead. Unavailable evidence stops the same way, without the label. With no staged change and no intersection, in the main checkout run `git merge --no-ff <branch>` with Git's default message: no `-m`, no `-F`, no edited message (the queue's Input 3 finds merged units by the subject `Merge branch '<branch>'`). If it exits non-zero, run `git -C <main> rev-parse -q --verify MERGE_HEAD`. Exit 1, no merge in progress: Git refused before starting (a path changed after the gate, or untracked content that is not ignored in a directory/file collision the exact-path comparison misses); stop as `dirty main: <paths Git names>` with Git's message, keeping everything as a gate stop does, and run no `git merge --abort`: there is no merge to abort. Exit 0, a merge in progress: a conflict; run `git merge --abort`, report and preserve the child/worktree. Any other exit is unavailable evidence: stop, keeping everything. When `git merge` exits 0, capture the merge SHA, then explicitly compare `git rev-parse HEAD^{tree}` with `git rev-parse <branch>^{tree}`. Inequality stops cleanup. Run checks again only when project rules explicitly require them after merge; ordinary “after changing code” requirements are satisfied by the child's verified results. Post-merge check failures stop with evidence preserved.

## Cleanup

1. After tree equality and required post-merge checks succeed, run `child-session close <name>` using the resolved executable and recorded window name, then require `child-session alive <name>` to exit 1.
