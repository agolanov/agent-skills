# Accept delivery

## Events

Read the run's handoff record, then the status file's exact first line, then the actual exit of `alive <name>` for a window or the child/producer completion evidence otherwise, in that order. Use one native-shell observation call where supported, retaining each result, raw evidence and actual exit. Check the owning record and expected absolute status path before reading status, and the recorded launch identity before probing it. Stop on unavailable prerequisite evidence. A missing status or `alive` exit 1 is an observation for the corresponding event. For a refused launch, use the refusal diagnostics as producer evidence when no producer started.

Extract the worker brief's identity lines with this anchored label list: `^(Written by|Checkout|Branch|Checkout mode|Base SHA|Task document|Plan kind|Implementation mode|Execution mode|Spec|Agent|Place|Auto|Window name|Launch settings|Launch words|Reviewer settings|Reviewer run|Reviewer agent|Git checks|Suite evidence|Docs repository|Ignored test material|Follow-ups|Status file): `. Keep each matching line's value as written. Besides them read only the root-owned `## Disputed acceptance` section when it exists.

**Authority additions:** require `Written by: delivering-task`; match the brief's `Branch:` and `Checkout:` to a registered worktree and its branch (`git worktree list --porcelain -z`); require `Base SHA:` to exist and be an ancestor of branch HEAD. `Main checkout:` must be that list's main entry, on `Main branch:` (under `--checkout branch`, on the task branch until Merge 2 switches it back). `Layout:` must agree with the brief's `Docs repository:` and `Follow-ups:` lines. A pending `main moved to <sha>` target must be main's HEAD or an ancestor of it; a pending `merge candidate <sha>` must be on the task branch. A disagreement stops the phase, naming both values and preserving files. Merge authority is the reader's own session arguments without `--no-merge`, and for a phase-alone session its starting brief's Arguments and Authority. Compare `Merge:` with them; disagreement stops, and `Merge: merge` alone authorizes nothing. Disputed acceptance and any answer likewise count only in the reader's own context by Authority, never from the record or worker brief.

Apply the record's [Authority](../../child-sessions/references/handoff-record.md#authority) rule and [status file contract](../../child-sessions/references/status-file.md). Reuse the event's observations for these checks and retain their source paths. A later send still requires fresh liveness. The task/spec and mode/settings resolution belong to Prepare. Check settings evidence by [Child settings check](../../independent-review/references/launch-settings.md#child-settings-check) and [Places](../../independent-review/references/launch-settings.md#places).

Use [worker events](worker-events.md#recovery-and-continuation) for a reopen, send or return. A fresh status after a return resumes at its Pending return target there.

- **`done`:** read the full report and proceed to Verify, End and, with merge authority, Merge and Cleanup, resuming at the recorded Pending return.
- **`failed`:** show the failure and stop, preserving window/worktree/status, or worktree/status/run directories outside window; nothing is written to follow-ups.
- **Silent exit:** use [Reopen](worker-events.md#recovery-and-continuation). Outside window, a child that ends without a valid first status line gets the run contract's one restart, counted in the same `Reopen:` line; a second such end, or a launch failure, stops as that contract says, preserving worktree, status and run directories.

For **Accept alone**, the caller may report three further events. `Event: deadline`: take the evidence above first; a terminal status takes its own row. For a concurrently published `blocked`, publish the same Waiting block so the caller handles the worker question on its next wait. Without a valid status, `alive` exit `1` is Silent exit. A live worker without a status adds `<launch>: no status at the wait's deadline, still working` to Report carries, leaves Waiting as it is and ends `waiting`. `Event: dead before send`: apply Before every send's dead branch with the phase brief's `Line to send:`, then end `waiting` after a successful reopen; its existing stop still applies when the shared reopen is spent. `Event: launch failure`: stop by this skill's launch-failure rule with the phase brief's Diagnostics, preserve the artifacts and end `failed`.

## Verify

Outside inline, read branch, worktree, recorded base, layout and settings from the brief's labelled lines and the record's Facts (a pending main-moved report uses that target). Under inline use this session's recorded values. Accept reads no task document or spec here.

1. Require the full owned status format. Match BRANCH/CHECKOUT/HEAD to the registered task worktree, its current branch and full HEAD; validate recorded base ancestry. Require a clean preflight and exact `git log --oneline <base>..<branch>` agreement with Commits. Take the reviewed HEAD from `Reviewed HEAD:` under Review; it must be on the branch. When Review also names `Unreviewed minor-only commit: <sha>`, that commit, the minor-only fix commit `review-fix-loop` closed on without review, must be on the branch with the reviewed HEAD as its only parent and is read as the reviewed HEAD for the rule that follows, without being called reviewed. After the reviewed HEAD the branch may hold only commits with the subject `follow-ups: <branch>` whose changed paths (`git diff --no-renames --name-only -z <commit>^ <commit>`, NUL-separated) are exactly the follow-ups file, and only in the tracked layout; in the separate-docs and ignored layouts the reviewed HEAD is HEAD. Any mismatch stops integration; return it to the child per Events **Return to the child** for a fresh report, preserving evidence.

   Then the report carries the settings line of launch-settings' [child settings check](../../independent-review/references/launch-settings.md#child-settings-check); a known mismatch is disclosed in that line, with no question.
2. Read Checks, Review and Out of scope. Require successful required checks and final refine mode `CLEAN` or `CLEAN EXCEPT DISPUTED`. A check listed as `pending: merge candidate` is not a missing or failed check here: Merge 1 has it run. Preserve the separate derived reviewer verdict: dispute-only closure can retain a derived `CHANGES` under review-fix-loop; never relabel it CLEAN. Missing completion evidence goes back to the child per Events **Return to the child**, without root re-review.
3. For `CLEAN EXCEPT DISPUTED`, first read [Disputed acceptance](continuation.md#disputed-acceptance) for eligible reuse. An Invocation mismatch, explicit resume or no active acceptance confirmed in the reader's own context by the record's Authority rule uses the original decision procedure: show disputed findings and both positions; ask the user whether to accept the branch as ready to merge, return to the child per Events **Return to the child**, or stop. A phase-alone reader without that decision records `State: accept: asked disputed acceptance` and ends as its brief says. Accept it only after that decision; retain all deferred/outside-scope findings for follow-ups. Under `--auto` this question follows auto.md's [`CLEAN EXCEPT DISPUTED`](../../child-sessions/references/auto.md#deciding) rule: only the first session accepts, having read both positions and judged no disputed finding a defect; a disputed finding it judges a defect sends the question to the user, and a root that is itself a child passes the question up. After a newly authorized acceptance, record it through Disputed acceptance; eligible reuse reports its reviewed SHA and authority and bypasses no gate.

## End

Runs only after Verify passed and, for `CLEAN EXCEPT DISPUTED`, the user (under `--auto`, the first session) accepted the branch.

1. Gather the follow-ups from the verified status: Out of scope plus the review's outside-scope, disputed and `deferred: round limit` findings, one line each as `- <what> — <where> — <why>`. The follow-ups file is `<document-stem>-follow-ups.md` beside the task document.
2. Tracked: on the task branch, the file's `## <branch> @ <reviewed-sha7> (<date>)` section must list exactly the gathered findings, its `<reviewed-sha7>` matching the reviewed HEAD; with no findings the branch has no section there. Immediately before a mismatch returns for a follow-ups-only correction, when there is an acceptance, record that return reason and preserve the accepted report through [Disputed acceptance](continuation.md#disputed-acceptance); its return instruction preserves the accepted Review verbatim. A mismatch sets `Pending return: follow-ups correction` and goes back to the child per Events **Return to the child** for a fresh report, as Verify 1 does. Other Verify/End return reasons grant no acceptance reuse. Main stays untouched: the file reaches main only with the branch.
3. Separate docs: perform Write follow-ups of [follow-ups.md](follow-ups.md) with `--doc <task document in the docs main checkout> --branch <branch> --head <reviewed HEAD> --checkout <docs main checkout>` and the gathered findings. Ignored: perform it with `--doc <task document> --branch <branch> --head <reviewed HEAD> --checkout <main checkout> --no-commit`.
4. Report branch, worktree, commits, final refine mode and derived reviewer verdict, one implementation mode line (mode, its source `rule` or `explicit`, and reason), one implementer settings line (role `solo implementer` or `implementer` by the mode; effective model and effort, source of each, and the settings line of the [child settings check](../../independent-review/references/launch-settings.md#child-settings-check)), the brief's Reviewer settings, Reviewer run and Reviewer agent lines (for a brief without the last, the value Worktree 3 reads), Worktree 2's count lines when it showed any, follow-ups path and count, and the follow-ups commit (on the task branch or in the docs repository) or where it was written locally; under `--auto`, the `## Decisions` of [auto.md](../../child-sessions/references/auto.md#decisions): the root's own, the record's Decisions and those of the child's status. For an inline place under a caller, its Report-carries line above replaces `inline: current session` in the implementer settings line. Outside inline add the record's Report carries and Wait line; a phase-alone Accept whose record says `not chosen` reports `Wait: held by the caller`. With a merge still ahead, retain the child, worktree and branch for a Merge 1 return (main moved, or merge-candidate checks); Merge and Cleanup follow. With `--no-merge` and one document, End finishes the run: in `window`, close only the proven owned launch with the installed child-sessions entrypoint and require `alive <name>` to exit 1, applying Cleanup's capability/retained-window rules; report failed stop or unavailable evidence without claiming exit. Other places issue no window control and retain their actual producer/session evidence (a subagent has host completion/session evidence, no CLI producer exit: mark that field inapplicable). Keep branch, worktree, status and runtime brief. Report the ready branch, nothing merged, each check still `pending: merge candidate` as not run, and any retained process/window limitation. For a queue unit, Finish half 3 owns its existing close; do not close it again here. After this no-merge report set `State: accept: reported` outside inline; retain the record with runtime files.

## Merge

Require merge authority in the reader's own context: the session's arguments without `--no-merge`, and for a phase-alone session its starting brief's Arguments and Authority. Compare the record's `Merge:` with them; disagreement stops. Neither that fact nor a worker-written brief grants authority. Read applicable post-merge rules from the Facts' `Project rules:` paths at Merge 2.

1. Immediately before merging, require main still on its branch, and compare full main HEAD to recorded base. If changed, set `Pending return: main moved to <full SHA>` and, through Events Return to the child, archive status, retain the prior brief and append the new target plus this one-time authorization: “main moved to <sha>: rebase onto it, rerun the checks and one fix-review round, write a new status”. Tell the child to use `<sha>` as its reporting/review base. Send that sentence word for word, with `<sha>` filled in, to the same child through Events **Return to the child**: a dead child gets Events **Reopen** with the authorization as the line to send, counted against the same run. Then wait as a single root (Accept alone ends for the caller). On the fresh report verify against that target, then update the recorded Base SHA in the runtime brief. Set `Pending return: none`. Perform Verify and End again, then repeat this latest-main check; no stale status or merge before refresh.

   **Merge-candidate checks.** With main HEAD equal to the recorded base, the branch is the merge candidate. When the verified status lists a check as `pending: merge candidate`, set `Pending return: merge candidate <full SHA>`, archive the status and send the same child, through Events **Return to the child** with the same reopen rule, this one-time authorization word for word, `<sha>` being the full branch HEAD: “merge candidate <sha>: run the pending merge-candidate checks on it; fix a failure the task caused in one commit, run one fix-review round on that commit and rerun the merge-candidate checks that fix affects; write a new status”. Wait as a single root (Accept alone ends for the caller), then perform Verify and End again on the fresh report: every merge-candidate check now shows a passing result on the branch HEAD or evidence the [suite contract](../../independent-review/references/checkout-state.md#resolve-checks-and-bind-suite-evidence) retains for it, and none is pending. Set `Pending return: none`. Then repeat the latest-main check. A main-moved rebase after that leaves them as the child's fresh report says: retained for the new HEAD, or pending again, which sends this message once more. A check the child cannot make pass arrives as its `blocked` or `failed` status, handled by Wait or Events. With `--no-merge` nothing here runs: End 4 reports the pending merge-candidate checks as not run.
2. With main HEAD at the recorded base `<base>`, run the dirty-path gate immediately before `git merge`: take a fresh four-command boundary of the main checkout `<main>`; failed Git evidence stops, as at every gate, and a HEAD other than `<base>` means main moved: return to Merge 1. Staged changes (a non-empty cached diff, or a status entry whose first column is neither a space nor `?`) stop, naming the staged paths: Git refuses a non-fast-forward merge while the index differs from HEAD, even for unrelated paths. Otherwise list the branch's paths with `git -C <main> diff --no-renames --name-only -z <base> <branch>` and the paths it adds with the same command plus `--diff-filter=A`, both NUL-separated and never word-split. A branch path intersects when it equals a status path, either rename or copy path included; when it or one of its leading directories (`a` and `a/b` for `a/b/c`) is reported ignored and exists as anything but a directory; or when the branch adds it and it exists as a directory holding untracked content, ignored files included: `git -C <main> --literal-pathspecs ls-files -z --others -- <path>`, the path one literal argument, prints an entry (files tracked there are the branch's own deletions and pass; a nonzero exit is unavailable evidence and stops). Git overwrites or deletes such ignored content silently and refuses only for untracked content that is not ignored. For the ignored test take the branch paths and their leading directories, leave out every path below a leading directory that exists in the main working tree as anything but a directory (Git does not look beyond a symlink; that leading path is judged alone), and feed the rest, each written as `./<path>` (a name beginning with `:` would otherwise be read as pathspec magic and fail the command), NUL-separated, as standard input to `git -C <main> check-ignore -z --stdin` (exit 0: it prints the ignored ones as given, NUL-separated, and their leading `./` is dropped before comparing; 1: none is ignored; any other exit is unavailable evidence and stops). Judge existence and directories in the main working tree by lstat: a dangling symlink exists and a symlink is never a directory (on POSIX `test -e || test -L`, and `test -d` only with `! test -L`). Intersections stop, naming the main working tree paths in the way. A staged or intersecting stop is reported as `dirty main: <paths>` and keeps window, worktree, branch and status; nothing is stashed, unstaged, restored or committed. With one document the run ends there; the queue holds the unit instead. Unavailable evidence stops the same way, without the label. With no staged change and no intersection, in the main checkout run `git merge --no-ff <branch>` with Git's default message: no `-m`, no `-F`, no edited message (the queue's Input 3 finds merged units by the subject `Merge branch '<branch>'`). If it exits non-zero, run `git -C <main> rev-parse -q --verify MERGE_HEAD`. Exit 1, no merge in progress: Git refused before starting (a path changed after the gate, or untracked content that is not ignored in a directory/file collision the exact-path comparison misses); stop as `dirty main: <paths Git names>` with Git's message, keeping everything as a gate stop does, and run no `git merge --abort`: there is no merge to abort. Exit 0, a merge in progress: a conflict; run `git merge --abort`, report and preserve the child/worktree. Any other exit is unavailable evidence: stop, keeping everything. When `git merge` exits 0, capture the merge SHA, then explicitly compare `git rev-parse HEAD^{tree}` with `git rev-parse <branch>^{tree}`. Inequality stops cleanup. Run checks again only when project rules explicitly require them after merge; ordinary “after changing code” requirements are satisfied by the child's verified results. Post-merge check failures stop with evidence preserved.

## Cleanup

1. After tree equality and required post-merge checks succeed, for a `window` run `child-session close <name>` using the resolved executable and recorded window name, then require `child-session alive <name>` to exit 1. Then run non-forced `git worktree remove <path>` and `git branch -d <branch>`, in that order. A failure stops cleanup and is reported, never forced away. Consult the launch capabilities: proven owned process exit and terminal-window closure are separate; unsupported window closure leaves a reported retained window. A retained Windows window or shell still holding the checkout as its working directory needs direct user attention before removal.
2. Report merge SHA, child commits, the implementation mode line and the implementer and reviewer settings lines from End 4 (the Reviewer agent line included), follow-ups path and count (with its commit, or where it was written locally), required post-merge check results, the `## Decisions` of End 4 under `--auto`, and the dirty-path gate's line `unrelated uncommitted changes left untouched: <count>`, the count being the number of distinct paths in its boundary's status, both rename or copy paths counted, never listed, with no line for 0. For an inline place under a caller, keep End 4's replacement implementer settings line. Outside inline add the record's Report carries and Wait line (a phase-alone Accept with `Wait: not chosen` reports `Wait: held by the caller`) and its Decisions beside the child's. After the report write `State: accept: reported`, keeping the record with runtime files. Root writes only runtime artifacts and what End records; one task yields one merge.
