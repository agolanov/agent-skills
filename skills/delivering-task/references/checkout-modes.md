# Delivery checkout modes

## Checkout mode

`--checkout` chooses where the implementer works: `worktree`, the default, in a new worktree as Worktree says; `branch`, on a new task branch in the main checkout itself; `main`, directly on the main branch in the main checkout. The user's words choosing one count as the key. The other sections apply as written, except where the steps below replace or add to them.

1. **Refusals.** Preflight 2 resolves the mode: on `--resume` it is the brief's recorded `Checkout mode:` line, a brief without that line recording `worktree`; an explicit `--checkout` naming another mode stops, naming both. Stop before anything starts, naming the key and its value, for: a value other than these three; `branch` or `main` with several documents or a directory, or in a phase-alone session (a brief or prompt carrying a `Phase:` line); `main` with `--no-merge` (the commits land on main, nothing is left to merge) or with `--branch` (no task branch is created).
2. **Names under `main`.** The task branch is the main branch: the brief's `Branch:` line, every Git command naming `<branch>`, and the follow-ups' `--branch`, section heading and `follow-ups: <branch>` commit subject use the main branch's name. Runtime files (`<runtime>/<branch>-brief.md`, the status, the handoff record), the record's `Run:` and the window name keep the name Preflight 2 derives from the document stem: runtime names are shared by every project and run.
3. **Checkout.** Worktree 1 does not apply: the checkout is the main checkout. Under `branch`, a new run stops when the derived branch exists, naming it, unless `--resume`. In Worktree 2, before any document commit, take a four-command boundary of the main checkout: every status path other than the task document and its spec stops the run before any commit, branch or window, naming the paths, because the implementer commits in this checkout and other work would join the task or block the branch switch. Nothing is stashed, committed or discarded; ignored files do not count. Worktree 2's commits and count lines then apply as written, and in place of `git worktree add` record full main HEAD as `<base-sha>` and, under `branch`, run `git -C <main> switch -c <branch> <base-sha>`, verifying the main checkout's branch and HEAD; under `main` create nothing. The brief's `Checkout:` is the main checkout's path and its `Checkout mode:` line `<mode> (<default|explicit>)`.
4. **Branch of the main checkout.** Under `branch`, from the switch until Merge 2 switches back, the main checkout stands on the task branch: Preflight 1's and Phases' requirement that it be on its main branch reads as on the task branch, and Worktree 3 matches the brief's `Branch:` and `Checkout:` to that entry. Merge 1 compares the main branch's ref, `git -C <main> rev-parse refs/heads/<main branch>`, with the recorded base. Merge 2 first runs `git -C <main> switch <main branch>` (a failure stops, keeping everything, with Git's message), then its dirty-path gate and merge as written. Cleanup 1 closes the window as written and runs `git branch -d <branch>` only, removing no worktree. A report written before that switch (a stop, a `failed` status, `--no-merge`) says `main checkout left on branch <branch>`.
5. **No merge under `main`.** Main's HEAD is the task's last commit, so Merge 1's latest-main comparison and Merge 2 do not run. Merge-candidate checks run as written, main's HEAD being the candidate. Checks the project rules require after merge then run on main's HEAD, and Cleanup 1 closes the window as written, removing no worktree or branch. Cleanup 2 reports `task commits on <main branch>: <base7>..<head7>` in place of the merge SHA and no dirty-path count line. A stop or a `failed` status leaves the task's commits on main, reported with the same line; nothing is reverted.
6. **Reports.** End 4 and Cleanup 2 add the line `Checkout mode: <mode> (<default|explicit>)`.
