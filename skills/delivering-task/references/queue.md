`delivering-spec-stages/references/stage-derivation.md` holds a display copy of Input 3's merged-subject search and leftovers list and of Input 5–6; keep them equal.

# Queue

`delivering-task` with several documents or a directory: the documents become units delivered in dependency order, independent ones in parallel in visible child sessions up to `--parallel N` (one at a time outside `window`), merged in order of readiness. Under `--auto`, every question below that would go to the user is routed by [auto.md](../../child-sessions/references/auto.md#deciding), and every unit's brief says `Auto: yes`.

The root writes no code, except under `--run inline`, where it is every unit's implementer. Per-unit work is the sections of `delivering-task`'s [SKILL.md](../SKILL.md), performed exactly as written, with the run's `--agent` and `--run <place>`, each unit's execution mode and implementer settings (Preflight 4) and the `--reviewer-run`/`--reviewer-model`/`--reviewer-effort` flags passed to every unit. Every brief and message a child receives (implementer brief, main-moved authorization, continuation line, answers) is `delivering-task`'s or `child-sessions`' exact text, never a paraphrase. The queue only commits fresh units' documents (Preflight 4 Documents), decides when each unit starts, waits and merges, and records states in its state file. `--parallel N` (default 3) bounds live agents (Scheduling 3) in `window`; other places run one unit at a time ([Places](#places)).

## Places

`--run` places every unit's implementer, decided once for the run in Preflight 3. `window`, the default, runs as the sections below say. With `--run inline`, `subagent` or `background` the units run one at a time in queue order, and `--parallel` given with such a place stops the run before anything starts, naming `--parallel` and the place. One at a time changes these sections:

- **Scheduling:** step 1 still decides what is startable; steps 2–3 do not apply. The earliest startable unit in queue order starts whenever no unit of the run is `running`, `blocked`, `rebasing`, `done awaiting merge` or `merge held`; no other unit's work is open, so no overlap hold is needed.
- **Start half:** the unit's place subsection of `delivering-task` Open and wait (Subagent and background step 1, or Inline) replaces Open and wait 1.
- **Wait loop:** that subsection replaces it, here and wherever a later step goes back to the Wait loop. Its `done` makes the unit `done awaiting merge`, then Finish half; its `blocked` is answered there, the state `blocked: <question>` meanwhile; an early settings mismatch is handled as Wait loop 1 says; its `failed`, and any stop there, make the unit `failed: <reason>` as Wait loop 4 says, with no window to peek or close.
- **Finish half:** step 3's `close` and `alive` apply to `window` only.

## Input

1. Units, dependencies and order. Everything here happens before anything opens.
   - **Documents.** A list gives task documents in input order. A directory contributes every `*.md` file directly inside it (not recursive) except `*-follow-ups.md` and `*-tails.md`, in file-name order. A document under a `queues/` directory or whose first line starts with `# Task queue:` stops the run, naming it: "queue files are no longer read; pass the plans, or a directory holding them". Resolve each document as `delivering-task` Preflight 1 does: a spec with one plan becomes that plan; a spec with several plans is asked about once, here (under `--auto`, routed by [auto.md](../../child-sessions/references/auto.md#deciding)); a spec with none stops the whole run with that step's refusal. Two inputs resolving to the same document are one unit, at the first one's place. One unit per resolved document, named by its full stem (`2026-10-29-alpha`), its spec as that Preflight 1 finds it; branch and window are exactly what `delivering-task` Preflight 2 derives from it: no `--branch` override, no shortened names.
   - **Dependencies.** Before scheduling, read every resolved document and decide, for each later document against each earlier one in input order, whether it relies on it: it uses something the earlier one creates or changes (a file, function, section, key, skill name or behaviour), its checks rely on the earlier one's result, or the documents say so in prose. The sources, strongest first:
     - A resolved document may hold one line `**Depends on:** None` or `**Depends on:** <entry>, <entry>...`, each entry a document stem or a path relative to the project checkout; an entry matches the unit with that stem. A document with the line depends exactly on what it names, and the line replaces the inference for it. An entry naming no unit of the run is an out-of-run entry, settled by step 3 and, failing that, step 4.
     - The user's words about which tasks depend on which replace the inference for the pairs they cover; `--independent` replaces it for the whole run (the queue infers no dependency; a `**Depends on:**` line still counts).
     - Otherwise the inference decides. For a pair the root is unsure about, the later document depends on the earlier one (a wrong dependency costs only time); that serializes that pair only. A document without the line depends on nothing merely because it follows another in input order.
   - **Order.** A dependency cycle stops the run, naming its units. Queue order is a topological order that keeps input order among ready units: repeatedly take the earliest unit in input order whose in-run dependencies are all placed.
   - **Show** one line per unit, as information, with no question: `<unit>: depends on <unit>, <unit> | none — <reason>`. The reason names what the inference found (the thing used, the check relied on, or the prose), or `its **Depends on:** line`, or the user's words, or `--independent`; with `--independent`, a unit without a `**Depends on:**` line shows `none — --independent` (a unit with one shows its line).
   - **No merge.** With `--no-merge`, the units that depend on an undelivered unit of the run are held, decided at the end of step 3 (it needs the units step 3 finds merged).
2. Normalize states: `delivered <sha7>` is done; every other state is a candidate again, its dependencies re-evaluated against delivered units. States come from an earlier run's state file only when its header is identical to this run's: same form, same documents, same order ([queue-state-file.md](queue-state-file.md)); otherwise every unit is `ready`. When the runtime directory was cleared (logout, reboot) or the header differs, Git is the durable record: step 3 finds merged units by their merge subject, and steps 5–6 find leftover branches, worktrees and briefs.
3. Already merged: after Preflight 1–3 and before step 4's question, for each candidate take `<branch>` as step 1 says and search the first-parent history of the project main checkout's main branch (`git log --first-parent --merges --format='%H%x09%cs%x09%s' <main>`, merge commits only) for a subject equal, as a whole fixed string, to `Merge branch '<branch>'` or `Merge branch '<branch>' into <main>`; the most recent match counts. For each found unit show the merge's short SHA and date and ask once: record it `delivered <sha7>` (recommended), or deliver it again; under `--auto` that recommendation settles it ([auto.md](../../child-sessions/references/auto.md#deciding)). A recorded unit counts as delivered for dependencies and is no longer a candidate, so steps 4–6 never touch it. List its leftovers without acting on them: a worktree or branch under its name (Cleanup not done), a live window with its name (`child-session list`); finishing them is the user's call. Such a live window is a retained window under Scheduling 3: it counts toward `--parallel` while `alive` returns 0, but not for overlap (Scheduling 2), since its changes are already on main. A unit to deliver again stays a candidate; if step 6 then finds its leftovers, it recommends discard, since that branch is already on main. No match, no question. The same search settles each out-of-run `**Depends on:**` entry, with the entry's stem as `<branch>`: a match satisfies it without a question; no match leaves it for step 4.
   **No merge hold** (`--no-merge` only), once the units above are recorded and before step 4: nothing of the run is merged, so a unit depending on another unit of the run (directly or through other units) can never start. Record each such unit `not started: depends on unmerged <unit>`, naming a nearest unit it depends on that is not `delivered` (a dependency on a unit recorded `delivered` does not hold it). A held unit is not a candidate for steps 4–6, for Preflight 4's mode decisions and settings, or for the document commits: the run asks nothing and commits nothing for a unit that cannot start. Its leftover branch, worktree or window from an earlier run is not proven or resumed; list it in the report without acting on it, as for the units above.
4. Before any window, list the candidates with an out-of-run entry that step 3 left unsettled and ask the user once, for each such entry: drop that dependency, or skip the unit as `not started: depends on missing <entry>`; units depending on a skipped one, transitively, get the same state. The user decides; never choose for them. Under `--auto` this consent is routed by [auto.md](../../child-sessions/references/auto.md#deciding).
5. Once Preflight 1–3 are done (before Preflight 4), for each candidate whose branch, worktree (`git worktree list --porcelain -z`) or window (`child-session list`) exists under the names `delivering-task` derives, prove ownership as `delivering-task --resume` does: `<runtime>/<branch>-brief.md` (`<runtime>` comes from `child-session runtime-dir`) exists and names this task document and its spec; its Branch and Checkout match the registered worktree and branch; a live window with its recorded name lists the brief's checkout. No window is normal after a failure. A candidate with only an old brief or status and no branch, worktree or window is proven only when the brief names this task document and its spec and its Checkout is the path `delivering-task` Worktree 1 derives for this branch in this project (no brief: the status's CHECKOUT must be that path); runtime names are shared by every project, so anything else is another task's artifact. A missing brief where a branch, worktree or window exists, a brief there that lacks the `Written by: delivering-task` line (shown with `delivering-task` Worktree 3's message for such a brief), or any mismatch, stops the whole run before any window and before step 6 asks anything: report it, close, delete and rename nothing (branch deletion acts by name; child controls require the matching launch record); the user resolves it and reruns.
6. Only then show each proven unit's leftovers and last status and ask once per unit: resume through the `--resume` path of `delivering-task`, or discard: `close` the window if live, `git worktree remove --force <path>`, `git branch -D <branch>`, archive the old brief and status, then start fresh. Recommend resume when the status reported commits, and discard for a unit that step 3 found merged and the user chose to deliver again, since its branch is already on main. Under `--auto` the question reaches the user whenever discard is [hard to undo](../../child-sessions/references/auto.md#hard-to-undo), whatever the recommendation: `git log --oneline <main>..<branch>` prints a commit, or `git -C <path> status --porcelain=v1 --untracked-files=all --ignored` prints any entry (uncommitted changes, untracked files or ignored files, all of which `--force` deletes), or either command fails, since unavailable evidence proves nothing safe; otherwise it is routed by [auto.md](../../child-sessions/references/auto.md#deciding). A proven candidate with only an old brief or status cannot resume: show each file's path and the status's first line and Commits, or `no status file`, then archive them without a question. To archive, rename a file to its full name plus `-old-<n>`, `n` the smallest number whose name is unused (`2026-10-29-beta-status.md` → `2026-10-29-beta-status.md-old-1`), never replacing an existing file.

## Preflight

1. Project main checkout: the top level of the current repository; when that is a separate docs repository rather than the project, ask the user for the project checkout (under `--auto`, routed by [auto.md](../../child-sessions/references/auto.md#deciding)). Require it on its main branch; uncommitted changes are allowed and stay untouched. Docs repository = `git -C <document-dir> rev-parse --show-toplevel` for every unit's document, its toplevel the docs main checkout; all documents must share one, else stop before anything opens, naming them. Both layouts are allowed (documents tracked by the project, or a separate docs repository). Require docs main on its main branch the same way. Each check still takes a four-command boundary, and failed Git evidence stops.
2. Locate the installed `child-sessions/SKILL.md` with its references and its native platform entrypoint (absolute path, never PATH), with `<runtime>` from `runtime-dir`; read them completely. Everything else the queue performs is `delivering-task`'s own text.
3. Select the agent and decide the place as `delivering-task` Preflight 2 does, with its refusals; the one that depends on a unit's execution mode is checked in step 4. Run `delivering-task` Preflight 3 (child-sessions, which Input 3 and 5 need) once for that agent. A unit's execution mode depends on whether it resumes, known only after Input 6, so the implementer settings and the child's dependency check wait for step 4.
4. Execution modes and settings. Runs after Input 6, once every candidate is known to start fresh or resume, and before anything opens. For every unit still a candidate:
   - **Fresh unit:** take `--execution` when given (a unit for which the value is invalid for its document kind stops the run, naming the unit, the value and the kind); else perform `delivering-task` [Execution mode](../SKILL.md#execution-mode) on the unit's resolved document.
   - **Resumed unit:** keep the `Execution mode:` line its brief records. An explicit `--execution` different from the recorded mode stops the run, naming the unit. A recorded `Place:` other than the run's place stops the run, naming the unit and both places.
   - **Settings.** Resolve the model of each role the fresh units need (`implementer`, `inline implementer`) once for the queue per [launch settings](../../independent-review/references/launch-settings.md#precedence), for the run's place as launch settings [Places](../../independent-review/references/launch-settings.md#places) says; a pair the place cannot select and verify (under `subagent`) stops the run here, naming the place and the pair, before anything opens. A fresh unit gets a rule-decided mode as a caller-decided value (source `rule`), an explicit mode as an explicit `--execution`, and every field not set explicitly as a caller-resolved policy value of its mode's role; its inline effort comes per unit from that section's inline effort rule, under an explicit `--execution inline` too. Explicit `--model`/`--effort` values, `cli-default` included, are forwarded as explicit, and an explicit `--execution` to every unit. A resumed unit keeps its recorded mode and settings. Under `--run inline` nothing is resolved: every unit's implementer is this session.
   - **Dependencies.** Run `delivering-task` Preflight 4 (the child's dependency check in this queue's layout) once for the agent: it requires every execution skill a fresh or resumed unit's mode needs; missing dependencies stop before anything opens. Under `subagent`, a unit whose mode `delivering-task` Preflight 2 refuses for the place stops the run here, naming the unit.
   - **Show** one line per unit, as information before Scheduling, with no question: mode with its source, reason, model and effort (`inline: current session` under `--run inline`).
   - **Documents.** After the bullets above, commit the paths this step owns, the task document and then its spec (when not `None`) of every fresh unit, in queue order, each alone, in the repository holding it, `<repo>` = `git -C <document-dir> rev-parse --show-toplevel`: the step of `delivering-task` Worktree 2, done once here because a document commit on main after a unit opened would send that unit through a main-moved rebase at its merge. A unit Input 3 recorded delivered, Input 4 skipped, Input 6 resumed or Input 3 held by the No merge hold commits nothing. For each document take a fresh four-command boundary of `<repo>`; failed Git evidence stops. The document has uncommitted changes (untracked, staged or unstaged alike) when its exact repository-relative path `<rel>` equals a path of the NUL-delimited status, either path of a rename or copy entry included. With changes run `git -C '<repo>' --literal-pathspecs add -- '<rel>'`, then `git -C '<repo>' --literal-pathspecs commit -m 'docs: <basename>' -- '<rel>'`, each path and message one literal shell argument quoted for the shell that runs it (inside POSIX single quotes a single quote is written `'\''`; inside PowerShell single quotes it is doubled), and show `committed <rel> <sha7>`; without changes commit nothing. The pathspec commits the document alone: other staged changes stay staged, unstaged and untracked paths stay as they are, and when the document is one side of a staged rename only its own path is committed, the other side staying as it is. A failing `add` or `commit` stops the run before anything opens, reporting Git's error. A document Git ignores is skipped without a message. Then show `unrelated uncommitted changes left untouched: <count>` for the project main checkout and, in the separate-docs layout, `<docs main checkout>: unrelated uncommitted changes left untouched: <count>` for the docs repository: the number of distinct paths in the status of that repository's last boundary in this bullet, both rename or copy paths counted, other than a document committed here, never listed; a count of 0 shows no line. A repository with no boundary here (the project main checkout in the separate-docs layout, or either one when no unit is fresh) takes one for its count. The commits and counts are information, with no question. Each fresh unit's `delivering-task` Worktree 2 then normally finds nothing to commit; a document the user edits during the run is committed when its unit starts.

   The state file records no mode: a started unit's mode lives in its brief, and an unstarted unit's mode is decided again on a rerun.
5. Create the runtime state file per [queue-state-file.md](queue-state-file.md) with every unit in queue order and its normalized state.

In `window`, use each launch's `capabilities <name>` before terminal controls, with the matching checkout/launch record. A `peek` below is optional when unsupported: read the status/report instead. For an unavailable `send`, a live child receives answers directly from the user in its window (under `--auto`, answers the root decided, which the user only types in) and the queue keeps waiting through files; announce that limitation once when opening. Timeouts are not approval requests and dialog counts are not observable there. Keep the single reopen/alive checks from `delivering-task` Open and wait. Count live agents, including ones whose owned stop failed; a retained terminal shell after proven agent exit takes no slot. Report a retained window separately when window closure is unsupported.

## Scheduling

Runs at the start, at the end of each drain that merged (Finish half 2), and whenever a slot frees while no drain end is pending.

1. Startable: a candidate not yet started whose dependencies are all `delivered`; an out-of-run entry Input 3 found merged counts as delivered. With `--no-merge`, step 3 (No merge hold) already recorded the units that depend on an undelivered unit of the run as `not started: depends on unmerged <unit>`; they are not candidates, and nothing is recorded here.
2. Read [overlap.md](overlap.md). Hold back a startable unit that overlaps a unit with a live window (except a window left alive by a unit Input 3 recorded, whose changes are already on main) or an earlier unit chosen in the same pass; it waits until that window is gone, normally after its merge.
3. Live agents: `running`, `blocked`, `rebasing`, `done awaiting merge` (its agent stays alive for a possible main-moved return until Cleanup) and `merge held` (kept for its retry, Finish half 7), plus a `failed` window until `close` and `alive` returning 1, and a delivered unit's window whose Cleanup `close` failed, a `done: branch ready` unit's window whose `close` failed (Finish half 3) or a unit recorded by Input 3 whose window was left alive, while `alive` (rechecked at each Scheduling) returns 0. Choose startable units in queue order until live windows reach `--parallel`. If such retained windows (failed, stopped, delivered or ready, their `close` failed and `alive` still 0, or recorded by Input 3 and left alive) keep a startable unit waiting while no unit is working or awaiting merge, report them and ask the user: they close the window (recheck `alive`, then Scheduling again; a failed or stopped unit keeps its worktree, branch and status file), or the run goes to End with the waiting units `ready`. Under `--auto` the question is routed by [auto.md](../../child-sessions/references/auto.md#deciding); closing such a window is the user's own act, so a session answering without the user takes End.
4. Mark the chosen units `running` in the state file, then run their start halves.

## Start half

For each chosen unit in queue order, perform `delivering-task` Preflight 1–2, Worktree, Brief and Open and wait 1 (open), exactly as written, with the unit's resolved document, its execution mode and settings labelled as Preflight 4 decided them (a caller-decided mode or an explicit `--execution`; policy or explicit settings) and, for a unit Input 1 resolved from a spec, `--spec <that spec>`; a resumed unit takes its `--resume` path. The Wait loop below replaces Open and wait 2. Record branch, window, status file and base SHA in the state file. A stop inside the start half makes the unit `failed: <reason>` (Wait loop 4).

## Wait loop

1. Round-robin over windows whose agent is working (`running`, `rebasing`, a `blocked` window after its answer): one foreground `wait <name> <status-file> 150` per window per turn, then the next window, with the host's command timeout set above the wait (180 s or more) so the host can never move it to the background; a wait still running beside other commands is not the loop. Never 120 or less, never several waits in one shell call or in the background, never one long wait on a single window. A Codex tool yield is not a timeout: poll the same command as child-sessions says. `done awaiting merge` windows are not waited on again. At the first return of a unit's `wait` after each `open` of that unit (first open, reopen, resume), before its status is acted on, run the early [child settings check](../../independent-review/references/launch-settings.md#child-settings-check) for that opening and keep the matched record path. A mismatch makes the unit `blocked: settings` and asks the user to continue or stop (under `--auto`, routed by [auto.md](../../child-sessions/references/auto.md#deciding)), holding only that unit while the other windows keep going; stop is `stopped by the user` per step 4. A record not yet found, not yet unique or without the fields is left to the final check, which runs with `delivering-task` Verify in the Finish half.
2. Exit 0: read the first status line of every working window. Each `done` of a `running` unit becomes `done awaiting merge`; a `rebasing` unit keeps its state until its finish half ends. Then go to Finish half, or back to the loop when the hold allows none.
3. `blocked`: state `blocked: <question>`; answer it per `delivering-task` Open and wait 3 and 5 (a stop there, its one reopen already used, counts as `failed`, step 4); back to its previous state (`running` or `rebasing`). A hold set on the unit persists throughout. Other windows keep going.
4. `failed`, unlike the stop of `delivering-task` Open and wait 3, because an interactive agent stays alive after writing `failed` and would hold a slot: state `failed: <reason>` in the state file only, `peek <name> 40` for the report, `close <name>`, free the slot only once `alive <name>` returns 1 (a failed `close` is Scheduling 3's retained window). Keep worktree, branch and status file. Its dependents, transitively, become `not started: depends on failed <unit>`; other units continue. Run Scheduling unless a drain end is pending (the drain's end runs it), then drain (Finish half 2). A unit the user stops is `stopped by the user`, handled the same way, except that its dependents, transitively, become `not started: depends on stopped <unit>`.
5. Exit 124: `peek <name> 40` and handle what it shows per child-sessions Dialogs, then the next window. Exit 3: `delivering-task` Open and wait 4's single reopen, shared with its step 5; a second silent exit or any other error counts as `failed`.

## Finish half

1. One finish half at a time. Pick, among `done awaiting merge` units, the one whose status file has the earliest modification time, not the window whose wait returned. The hold: from a main-moved return (step 4) until that unit is `delivered`, `failed` or `stopped by the user`, through any block, Verify return or `merge held` (step 7), the only finish half allowed is that unit's, once its fresh status says `done`.
2. Drain: whenever a finish half is allowed (after a Wait loop exit 0, a delivery, a failure or stop, a Verify return), run it at once; the Wait loop runs only while none is allowed. A merge leaves a drain end pending (step 6). With none pending, a drain has no end step: when no finish half is allowed, go back to the Wait loop. While it is pending, a held unit's rebase belongs to the drain: the drain ends when no finish half is allowed and the hold is not set. Then the drain end clears the pending mark and runs Scheduling and the start halves; then go back to the Wait loop.
3. Perform `delivering-task` Verify and End, then Merge and Cleanup, exactly as written; the merge keeps Git's default message (no `-m`), which Input 3 relies on. With `--no-merge`, perform Verify and End only, then close the unit's window, since no main-moved return can reach it: a main-moved return cannot occur without a merge, so steps 4 and 7 and the hold never apply. Run `close <name>`, then `alive <name>` must exit 1 (a failed `close` is Scheduling 3's retained window). Keep its worktree, branch and status file and record the unit `done: branch ready` with its follow-ups path and count. The closed window frees its slot and releases the overlap hold (Scheduling 2): run Scheduling, as Wait loop 4 does (no drain end is pending, since nothing was merged), then drain (step 2).
4. Merge returns the child for main-moved: state `rebasing`, base SHA updated as `delivering-task` Merge 1 records it, back to the Wait loop with the hold set. Fresh `done`: this unit resumes at Verify. `failed`: Wait loop 4, which releases the hold; drain.
5. Verify or a disputed-findings decision returns the unit to its child: a `rebasing` unit stays `rebasing` and keeps the hold, any other becomes `running` (nothing merged, no hold); drain.
6. Merged and cleaned up: `delivered <sha7>` with follow-ups path and count (a Cleanup failure is reported; the unit is still delivered, and a window left alive keeps its slot per Scheduling 3); a drain end is now pending. Read the first status line of every working window as Wait loop 2 does, then drain (step 2).
7. A `dirty main: <paths>` stop of `delivering-task` Merge (its dirty-path gate, or Git's refusal: no merge commit, no merge in progress) is not `failed`: state `merge held: <paths>`; window and agent, worktree, branch and status stay, and the unit keeps its slot (Scheduling 3). Show the paths, with Git's message after a refusal, and ask the user once: retry, after they have committed, unstaged, moved or removed their changes on those paths, or stop. Under `--auto` the question is routed by [auto.md](../../child-sessions/references/auto.md#deciding); those changes are the user's, outside the run's paths, so a session answering without the user answers stop. The question shares only the timing of a `blocked` one (Wait loop 3): synchronous, the other windows working on meanwhile; nothing is sent to the child and its status is not archived. Retry runs the unit's finish half again from `delivering-task` Merge 1, which still returns it for main-moved (step 4) when main moved meanwhile (for example the user committed their changes on those paths); a second `dirty main` stop asks again. Stop is `stopped by the user`, per Wait loop 4. Any other stop before the merge commit is `failed: <reason>` (conflict) or `stopped by the user`, both per Wait loop 4. A stop after it (tree inequality, failed required post-merge check) leaves main suspect: record `failed: <reason>`, start and merge nothing more, go to End leaving other windows as they are.

## End

When no window is working or awaiting merge and nothing is startable, report a table `unit | state | merge SHA | follow-ups path | follow-ups count` (a unit recorded by Input 3 shows `delivered <sha7>`, that short SHA as merge SHA, and `-` for follow-ups path and count, since its follow-ups were recorded, or not, outside this run; a `done: branch ready` unit shows `-` as merge SHA).

Then report every unit never started with its reason, and the kept worktree, branch and status file of each failed unit, and the leftovers listed for each unit recorded by Input 3. With `--no-merge`, report each ready branch with its worktree and status file: nothing of the run was merged. Report Preflight 4's count lines again, when it showed any. Under `--auto`, end with the `## Decisions` of [auto.md](../../child-sessions/references/auto.md#decisions): the root's own and those of every unit's status.
