# Prepare delivery

Run Preflight, Worktree, Brief and Launch in order. For a new non-inline run also use the [delivery record](delivery-record.md). For a phase continuing from a handoff, read its [delivery record](delivery-record.md), keep this run's branch, checkout, worker and runtime paths, and continue at the recorded question with the answer supplied by the caller. Start no second worker and perform no new-run commits.

## Preflight

1. Resolve the main checkout, main branch, the absolute task document path, and applicable project rules. Require the main checkout on its main branch; uncommitted changes are allowed and stay untouched. Use the ordinary Git boundary. When resuming in checkout mode `branch`, use the branch-mode main checkout rule. Recognise the document without reading it through: use its name and place, the header searches task document paths names, and its last line and the freshness recipe for its review mark:
   Read [task document paths](../../planning-task-docs/references/document-paths.md) for location/kind, plan/spec pairs and discovered candidates, then apply:
   - **Plan**: find its spec by that reference, with `--spec` first; without a match use `None`, with no question.
   - **Spec**: find its plans by that reference. None: refuse before any worktree or window, telling the user to write the plan with `planning-task-docs`. One: that plan is the task document, this spec its spec. Several: list them and ask the user which one to execute (under `--auto`, routed by [auto.md](../../child-sessions/references/auto.md#deciding)).
   - **Other**: any other file is a task document implemented directly (a brief, a task text). Spec `None`.

   `--spec` is accepted only with a plan. Layout: the docs repository is `git -C <document-dir> rev-parse --show-toplevel`, named by its main-checkout absolute path. **Tracked**: it is the project and `git -C <main-checkout> check-ignore -q <document-dir>` exits 1. An unexpected exit stops. **Separate docs**: it is another repository (nested in an ignored directory or elsewhere); require its main checkout on its main branch the same way, uncommitted changes allowed and untouched. **Ignored**: it is the project and that `check-ignore` exits 0 (ignored without its own repository). Show the user the document's kind, its spec and the layout, and the review-mark state of the task document and its spec per [review-mark.md](review-mark.md): fresh with verdict, reviewer and date; else `none` or `stale` with the failing freshness condition. Every mark state proceeds. Limit the Prepare reads to these evidence checks and the document reads in Implementation mode.

2. Select the agent, place and branch, then the [implementation mode](#implementation-mode) and settings. Use [launch choices](launch-choices.md) for refusals, settings precedence, reviewer options and resume. Resolve branch and window with [Delivery names](task-names.md#branch-and-window). Read [Checkout mode](checkout-modes.md#checkout-mode) only for `branch`, `main`, or a resume using those modes. Refuse unknown modes before work starts. Read the recorded checkout mode on resume, defaulting to `worktree` for an old brief. Under `worktree` use Worktree below. Announce non-window places and report the implementation mode and settings beside the document facts. A phase-alone inline place follows [Inline under a caller](launch-choices.md#inline-under-a-caller).

3. Resolve the installed child-sessions platform entrypoint and read its successful `runtime-dir`, outside Git. For a window follow its [Locate and open](../../child-sessions/SKILL.md#locate-and-open) and [Dialogs](../../child-sessions/SKILL.md#dialogs); for other child places follow [Launch and wait](../../child-sessions/references/run-contract.md#launch-and-wait). Direct inline uses the runtime for brief/status paths.

4. Resolve readable skills in the actual child's installed/project catalogs (this session's for inline), including checkout-local availability in the selected checkout. Require `review-fix-loop`, `independent-review`, `child-sessions` for a window reviewer, and the exact execution skill a plan's mode names. A missing dependency stops before opening: name it for installation.

## Implementation mode

Preflight 2 decides one implementation mode per run, after Preflight 1 has identified the task document and before any settings are resolved. The mode names the child's execution skill and its [launch settings role](../../independent-review/references/launch-settings.md#roles):

| Mode | Task document | Brief's Execution line | Role |
| --- | --- | --- | --- |
| `solo` | plan | `executing-plans` | solo implementer |
| `solo` | other | `None: direct implementation` | solo implementer |
| `subagents` | plan | `subagent-driven-development` | implementer |
| `direct` | other | `None: direct implementation` | implementer |

`subagents` is valid only for a plan, `direct` only for another document, `solo` for both.

1. **Given mode.** Refuse an invalid explicit `--impl` before worktree or launch, naming its value and the kind. An explicit `--impl` valid for the kind, a caller-decided mode (source `rule`) and, on `--resume`, the mode the brief records (Worktree 3) are taken as given. An explicit `--impl solo` on a large document is honoured, with no warning or question. The rule in step 2 runs only when none of these applies.
2. **Rule.** Read the document and choose, by your own judgement, the mode valid for its kind that will carry it out with the fewest tokens and in the least time.
3. **Settings.** Outside `--run inline`, pick the row of launch-settings' [work table](../../independent-review/references/launch-settings.md#roles) by the most demanding step of the task document, for every mode. Use the same document read as in step 2 when available. Fields with an explicit, recorded or caller-resolved value keep it.
4. **Output.** The mode; its source, `rule` (decided here or by the caller) or `explicit`; a one-sentence reason; model and effort, with the most demanding step that justified the row when step 3 chose it (the brief's `Launch settings:` line carries it as `effort step:`); or under `--run inline` `settings: none, --run inline`, since step 3 computes none. The brief records the mode as `Implementation mode: <solo | subagents | direct> (<rule | explicit>); <reason, one sentence>` and the concrete pair with per-field sources on its existing `Launch settings:` line.

## Worktree

Under `--checkout branch` or `main`, [Checkout mode](checkout-modes.md#checkout-mode) 3–4 replace parts of these steps.

1. Use the [worktree path](task-names.md#worktree-path). Resolve the main checkout and selected path, including existing symlinks. For a path inside the main checkout, run `git check-ignore`; if it is not ignored, tell the user and stop without changing ignore rules. For an external path, apply the same ownership/existence checks without an ignore prerequisite. For a new run only, refuse any existing branch or worktree, naming both, unless `--resume`; a phase continuing its own record keeps them.
2. For a new task (a `--resume` commits nothing), first commit its documents, the paths this step owns: in the tracked and separate-docs layouts, the task document and then its spec when not `None`, each alone in the repository holding it, `<repo>` = `git -C <document-dir> rev-parse --show-toplevel`. For each document take a fresh four-command boundary of `<repo>`; failed Git evidence stops, as at every gate. The document has uncommitted changes (untracked, staged or unstaged alike) when its exact repository-relative path `<rel>` equals a path of the NUL-delimited status, either path of a rename or copy entry included. With changes run `git -C '<repo>' --literal-pathspecs add -- '<rel>'`, then `git -C '<repo>' --literal-pathspecs commit -m 'docs: <basename>' -- '<rel>'`, and show `committed <rel> <sha7>`; without changes commit nothing. Each path and message is one literal shell argument, quoted for the shell that runs it (inside POSIX single quotes a single quote is written `'\''`; inside PowerShell single quotes it is doubled), and `--literal-pathspecs` keeps Git from reading a file name as pathspec magic. The pathspec commits the document alone: other staged changes stay staged, unstaged and untracked paths stay as they are, and when the document is one side of a staged rename only its own path is committed, the other side staying as it is. A failing `add` or `commit` stops before any worktree or window, reporting Git's error. The ignored layout commits nothing and shows no commit line, its documents never being committed; the count lines that follow still apply. Then show `unrelated uncommitted changes left untouched: <count>` for the main checkout and, in the separate-docs layout, `<docs main checkout>: unrelated uncommitted changes left untouched: <count>` for the docs repository. The count is the number of distinct paths in the status of that repository's last boundary (this step's, else Preflight 1's), both rename or copy paths counted, other than a document committed here; the paths are never listed, and a count of 0 shows no line. The commits and counts are information; the run continues without a question. Then record full main HEAD as `<base-sha>` and run `git worktree add -b <branch> <path> <base-sha>`; in the tracked layout that base includes the document commits, so the worktree holds the documents. Verify its branch and HEAD match. Keep runtime files under the helper's `<runtime>` outside Git, creating parent directories for nested branch names.
3. On `--resume`, follow [Resume delivery](resume.md) instead of the new checkout and document commits above.

## Brief

1. Read [implementer-brief.md](implementer-brief.md), fill every placeholder, and write `<runtime>/<branch>-brief.md`; status is `<runtime>/<branch>-status.md`. Fill `Auto:` with `yes` under `--auto`, else `no`. Persist task identity/base and the `Written by:`, `Place:`, `Implementation mode:`, Launch settings, Reviewer settings, Reviewer run and Reviewer agent lines for resume; under `--run inline` too, where the brief is the run's record for `--resume` and the queue and this session performs it ([Inline](../SKILL.md#inline)). Resolve required skill paths for the child's actual checkout/catalog, and provide the absolute owned status-contract path. Fill Layout facts: docs repository as Preflight 1 found it, named by its main-checkout absolute path even when it is the project itself; Follow-ups in the tracked layout is the absolute `<document-stem>-follow-ups.md` path beside the task document inside the worktree plus the absolute path of this skill's installed [follow-ups.md](follow-ups.md), otherwise `the root records them`; ignored test material is the test path the project rules state, else `tests/`, resolved against the main checkout to an absolute path; use it when it exists and `git -C <main-checkout> check-ignore -q <path>` exits 0, otherwise `None`. A stated path that fails either check is `None`, never replaced by `tests/`; before opening, tell the user which path failed which check, as information with no question, under `--auto` too. Use child-sessions' [brief checklist](../../child-sessions/references/brief-writing.md). Point the worker to the [status contract](../../child-sessions/references/status-file.md) by absolute path.

   Immediately after writing the brief, outside `--run inline`, create `<runtime>/<branch>-handoff.md` with `State: prepare: brief written`, using the [delivery record](delivery-record.md) format and Facts; each queue unit does the same with its state file in `Queue:`. For a new task first rename any earlier record to `<file>-old-<n>`, the smallest unused number; a continuing phase keeps its record and brief. Carry Preflight 2's announced non-window place and Worktree 2's count lines into Report carries. For the failed ignored-test-path notice above, read Told the user before giving it and append `ignored test material: <path> failed <check>` once the record exists. Inline creates no handoff record.
2. Keep the exact `Status file: <status-file>` line. A new task requires an absent status path; an existing artifact needs provenance validation or a stop, not silent reuse. The worker owns this status. On resume retain its brief and path, using Worktree 3 and the recorded continuation.

## Launch

Run the implementer in the place Preflight 2 decided.

### Window

1. Use the [window launch sequence](../../child-sessions/SKILL.md#locate-and-open) with `open --agent <agent> [--model M] [--effort E] [--cli-arg WORD]... <name> <path> <brief>`, quoting paths, passing the brief's recorded Launch settings as `--model` and `--effort` and omitting a field that is `cli-default`, and for a Claude agent the run contract's [lean launch](../../child-sessions/references/run-contract.md#launch-and-wait) words as `--cli-arg` values. Write these words on the brief's `Launch words:` line and the handoff record's [`Launch words:`](../../child-sessions/references/handoff-record.md#format) line before the launch (a root that writes no record keeps them on the brief) and pass the same words on every reopen and resume, a `--session-id` word with a fresh UUID. On explicit resume reuse the recorded window, the recorded Launch settings and the continuation brief; close any owned stale window before reopening, never an unrelated session.
2. Handle Startup and apply [window controls](worker-events.md#window-controls) to the actual launch.

### Subagent and background

For Prepare alone, record the start recipe below as `Action: start <place>` in [Waiting](../../child-sessions/references/handoff-record.md#waiting), with brief, checkout, settings and permission arguments, then complete Launch Record and end. The caller records the actual opening and performs the start; a single root performs it here.

1. Start the implementer in the worktree by run contract [Launch and wait](../../child-sessions/references/run-contract.md#launch-and-wait): a `subagent` with the pair Preflight 2 resolved, set by the host's native controls; a `background` CLI with the brief's recorded Launch settings, omitting a field that is `cli-default`, and the permission arguments of run contract [Permissions](../../child-sessions/references/run-contract.md#permissions), since the implementer writes and commits. Each `background` start or resume writes its run directory at `<runtime>/<branch>-run-<n>`, `n` the smallest unused number. On explicit resume start a fresh child from the continuation brief with the recorded Launch settings, never re-resolved.

### Record

Complete the record with `State: prepare: launched`, its identity, Facts, Report carries, Decisions and Told the user. Waiting names the launch and status with `Action: none` for a started worker, or the deferred start recipe above. Prepare alone ends here as its brief says, naming the record; a single root continues to Wait.
