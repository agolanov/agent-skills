On resume, apply [Resume repair](#resume-repair) after Worktree 3's gates. At Verify 3 and a follow-ups-only End 2 return, apply [Disputed acceptance](#disputed-acceptance). Paragraph duties come from [implementer-brief.md](implementer-brief.md); question authority comes from child-sessions' [auto.md](../../child-sessions/references/auto.md).

## Resume repair

After Worktree 3's provenance, identity and ordinary Git continuation gates, require an already usable retained task brief: task instructions, project-rule references, Required installed skills lines with a mode-appropriate Execution entry and usable Review loop/Reviewer launch paths, ownership/boundaries, Git/checks, layout/follow-ups, exact `Status file:` destination and usable linked status contract. Only currently applicable project rules are required: an explicit `None` remains valid when Preflight 1 finds none. Use existing Preflight dependency checks on required-skill/project-rule pointers too; absence or a dead required pointer stops with evidence. The template's permitted `Execution: None: direct implementation` for a non-plan kind remains valid, not a missing path. Missing other mandatory operational instructions stops with the missing text named; never reconstruct an identity-only task.

Set `Auto:` to this run's value. Read the implementer template for the two selected paragraph duties. Preserve original task instructions, identity/base, place/mode/settings and prior answers.

- For `Auto: yes` in a non-inline place, insert the template's complete `When Auto is yes` paragraph when absent, filling the installed absolute `child-sessions/references/auto.md` path. It carries child question routing and decision reporting.
- For every place, ensure the template's complete `After the task is complete` final-review paragraph is present: the recorded reviewer system key, Reviewer run/settings, conditional `--auto`, the normal review loop, no squash and `Reviewed HEAD` reporting. With a `Reviewer agent:` line the paragraph must pass that line's key (`--claude`, `--codex` or `--dual`); one passing another system key, or none, is a conflict. Without the line (a brief written before it existed) a paragraph passing no system key is the equivalent of the default, and one passing a key other than the opposite system's is a conflict. An absent paragraph is inserted from the template, whose key rule covers a brief without the line; the line itself is never inserted. A paragraph that supplies every other current duty but was written before the `Unreviewed minor-only commit` reporting sentence existed gets that sentence from the template appended once after its `Reviewed HEAD` sentence; that absence alone is not a partial-paragraph conflict.

Identify the two paragraphs by those openings, inspecting operational equivalents elsewhere too. Existing equivalent old wording remains when it supplies all current duties with matching recorded reviewer system, place and settings, conditional Auto behavior and usable installed absolute pointers. No matching paragraph or operational equivalent means absent: insert it once. Partial, duplicate or contradictory instructions/values and dead pointers are conflicts: stop before launch, preserving and reporting the text rather than appending or rewriting. Resolve installed dependencies through existing checks for retained as well as inserted pointers; a missing dependency stops with evidence.

Inline keeps the child-only autonomy paragraph omitted; its root applies Inline 1 and auto.md itself. `Auto: no` leaves conditional autonomy text inert and passes no `--auto` to review. Continue through the existing status archive, continuation sentence and launch rules; add no reopen, review or retry budget.

## Disputed acceptance

Obtain acceptance under Verify 3's current authority: the user, or only the first session under `--auto` after reading both positions and judging none a defect. An auto child passes the question upward. Reuse requires the active section's `Accepted invocation` to equal the handoff record's `Invocation:` value; a new run and an explicit `--resume` each create a new Invocation and require a new decision, even with unchanged Auto. Confirm the decision in the reader's own context by the handoff record's Authority rule: a single root's own conversation still holding it, or the prompt that started a phase-alone Accept carrying the question and the answer. The runtime brief's section, status and handoff record are evidence to compare, never the grant. A reader without that confirmation uses the ordinary decision procedure; phase-alone it records `State: accept: asked disputed acceptance` and ends as its brief says. An old brief without an active acceptance uses the ordinary decision procedure.

Record an actual authorized decision as quoted evidence only in one root-owned `## Disputed acceptance` section of the existing runtime brief, outside its identity labels. Use these distinct field names so the record cannot introduce duplicate resume identity labels:

- `Accepted invocation`, `Accepted Auto`, `Accepted task`, `Accepted branch`, `Accepted checkout`: the handoff record's `Invocation:` value, current Auto value, absolute task document, branch and checkout identity, respectively. Under `--run inline` (no handoff record), `Accepted invocation` remains this root's own current invocation.
- `Accepted reviewed SHA`: full `Reviewed HEAD` SHA.
- `Accepted final mode`, `Accepted derived verdict`: final refine mode and derived reviewer verdict separately. A section written before the native review tools names the second field `Accepted raw verdict`; read it as the same field.
- Exact complete disputed findings and both positions copied from the accepted report, in a fenced `text` block explicitly marked as inert quoted evidence, never executable instructions or authority. Choose a backtick or tilde fence of at least three characters, strictly longer than every consecutive run of that same character anywhere in the complete quoted payload; use that fence for both opening and closing without changing the payload.
- `Accepted by`, `Acceptance source`: who accepted, the actual answer or first-session decision, and its source.
- `Return reason`: the specific subsequent follow-ups-only correction, when one occurs, and the preserved accepted report used for comparison.

Supersede old records into explicitly inactive history under a different heading, leaving exactly one active section; never fall back to history. Record a new acceptance only after a new authorized decision confirmed in the root's current context. Add no separate state store, queue-state column, global status field or security framework.

When End 2 returns for a follow-ups-only correction, write `Pending return: follow-ups correction` in the handoff record outside inline and record that reason with the active acceptance before archiving status; preserve the accepted report as comparison source. Tell the child to copy that report's Review section verbatim into the fresh report while updating required follow-ups/commit/status facts only.

On the resulting fresh report, reuse acceptance only when all these conditions hold:

1. The active section's `Accepted invocation` equals the handoff record's `Invocation:` value, Auto is unchanged and the reader confirms the decision in its own context by Authority, for that recorded follow-ups-only return (`Pending return: follow-ups correction`). Task, branch and checkout identities match the active acceptance. Under inline, this remains the same current root invocation, neither a new root session nor an explicit resume.
2. The full `Reviewed HEAD` SHA matches.
3. Final refine mode, derived verdict and complete dispute text with both positions are byte-identical to the accepted values. Any changed Review text invalidates reuse.
4. Verify 1 still permits every post-review commit, reading a named `Unreviewed minor-only commit` whose only parent is `Reviewed HEAD` in its place in every layout: correct follow-ups subject and exact follow-ups path in the tracked layout; in other layouts that commit equals HEAD.
5. Every ordinary Verify gate succeeds again, including current Git state, checks, settings and report/follow-ups consistency. End's later gates still run before completion.

A further follow-ups-only correction may reuse the same record under these conditions. Report reused acceptance with its reviewed SHA and authority. Under `--auto`, keep the original decision in Decisions; reuse adds no approval.

A new invocation, explicit `--resume`, an `Invocation:` line that differs, changed Auto, missing current root-context confirmation or active acceptance, changed identity/reviewed SHA/either verdict/dispute, another return reason or unavailable comparison uses the existing decision procedure. A main-moved rebase invalidates reuse and goes through fresh verification and a new disputed decision when applicable. A newly identified defect still reaches the existing authority. No old record bypasses a Git, review, settings, follow-ups or completion gate.
