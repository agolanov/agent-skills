# Delivering Spec Stages

For each clean/path gate and continuation below and in child briefs, use the four ordinary Git commands and identity checks in [checkout state](../independent-review/references/checkout-state.md#direct-use-preflight), with process-local `GIT_OPTIONAL_LOCKS=0`, actual exits and raw output files. A clean gate requires successful commands and empty status and diffs; path gates parse NUL-delimited status and compare exact repository-relative paths, including both rename paths. Failed or unavailable Git evidence stops the dependent action. Use ordinary Git for other read-only checks, retaining real exits. Evidence has the reference's ignored/untracked-content, Git flags/normalization, nested-repository and transient-write limits. Stage/commit only owned paths; write, merge and push authority stays explicit.


`delivering-spec-stages <spec> [--agent claude|codex] [--execution inline|subagents|direct] [--model M|cli-default] [--effort E|cli-default] [--reviewer-model M|cli-default] [--reviewer-effort E|cli-default]`

The root writes no code and no document. Every stage's plan, review and delivery are sub-skills' sections, read from their installed SKILL.md files at run time and performed exactly as written, including each skill's own handling of its child's questions, settings checks, reopen budget and verification; every brief, question, verification and refusal is that skill's text, never a paraphrase. This skill decides what runs next (the choice each sub-skill leaves to the user), with which arguments and settings, records stage states in its [state file](references/state-file.md), and reports. It asks no question of its own: every question of a run is a sub-skill's, such as `delivering-task-queue` Input 6's leftover question, which Stage loop step 1 takes over.

## Preflight

1. **Spec.** Take from `splitting-spec-into-stages` Input exactly its project checkout and docs repository rules, its "no such file" stop, classification rules 1–3 (a plan or anything else is refused as there) and spec checks 1–3. Read check 3's `stages_parse` exits for this skill: exit 0 is a staged spec, the normal case; exit 1 with `no "## Stages"` is an unstaged spec, refused before anything runs, naming the spec: "no `## Stages` section; run `splitting-spec-into-stages <spec>` first"; any other exit 1 stops, naming the failed rule (the stderr line and the Parsing rule that words it); exit 2 stops as unavailable evidence. The splitter's checks 4–6 are not taken: a staged spec's plans are judged by Stage list 1's Unstaged plan check and by the Stage loop, and its Review mark is not checked: a stale or unmarked staged spec proceeds as it is. Then require the project checkout and the docs repository on their main branches, as `delivering-task-queue` Preflight 1 does; uncommitted changes are allowed and stay untouched. This skill does not take `delivering-task-queue` Preflight 4's **Documents** commit: stage plans are committed by `planning-task-docs`, and the spec is neither committed nor reviewed here: `executing-task-docs` Worktree 2 commits it when a stage is delivered.
2. **Skills.** Locate the installed `splitting-spec-into-stages`, `planning-task-docs`, `refining-task-docs`, `delivering-task`, `executing-task-docs`, `writing-task-follow-ups`, `child-sessions`, `delivering-task-queue` (whose Input 3, Input 5–6, Preflight 1 and Preflight 4 except its Documents bullet this skill performs) and `independent-review` (its checkout-state and launch-settings references, which the preamble and the settings rules link); read each SKILL.md and its references completely. A missing one stops before anything opens, named for the user to install. Resolve child-sessions' installed platform entrypoint by absolute path and set `<runtime>` from its `runtime-dir`; a terminal control this skill uses itself (Input 6's `close`) follows the launch's `capabilities <name>` as child-sessions says.
3. **Agent and settings.** Select the agent as `executing-task-docs` Preflight 2 does; every sub-skill gets it as `--agent`. Resolve once for the run, per [launch settings](../independent-review/references/launch-settings.md#precedence) for that agent, the `planner` and `refiner` settings from their role defaults, and the `implementer` and `inline implementer` settings as `delivering-task-queue` Preflight 4 Settings resolves them, the inline effort per stage; each stage's mode and implementer settings are decided in Stage loop step 4. `--model`/`--effort` set the implementer only and are forwarded as explicit. Validate `--reviewer-model`/`--reviewer-effort` once for the reviewer system, as `refining-task-docs` Preflight 2 does; they go to every `refining-task-docs` and `delivering-task` run (the reviewer flags below). Policy values go down as caller-resolved policy values (source `policy`), explicit ones as explicit. `--execution direct` stops here, naming the value and the kind: every stage document is a plan.
4. **State file.** Create it per [state-file.md](references/state-file.md) with its header; Stage list writes the lines after it.

## Stage list

1. **Stage lines.** Derive each stage's state (plan, merge found and leftovers named as Stage loop step 1 finds them, mark fresh or stale as Stage loop step 3 judges it); Stage loop step 1's settling and stops act when the loop reaches the stage. Apply the [display copy](references/stages-section.md#parsing-rules)'s Unstaged plan rule to the spec's candidates: an unstaged plan stops the run on the spec line, `spec | failed: unstaged plan <plan> | - | -`, naming the plan with the rule's message, "staged spec with an unstaged plan; remove or stage the plan". Write the stage lines (`pending`, the plan field the stage's one matching plan or `-`), show the list with each stage's derived state and go on to the Stage loop, with no question.
2. **Re-read.** Before every `refining-task-docs` run in the Stage loop, keep the stage list [`stages_parse`](../planning-task-docs/references/stages-section.md#recipes) gives; after it, run `stages_parse` again. A section that no longer parses stops the run, naming the failed rule. A stage of the kept list whose `NN<TAB>name` line is gone (renamed, renumbered or removed) stops the run, naming it, when it is delivered (Stage loop step 1 finds its merge) or is the stage the loop is at. Any other change is the new list.

## Stage loop

For each stage `NN` of the current list, in number order:

1. **Derive.** Find the stage's plan by Stage matching of the [display copy](references/stages-section.md#parsing-rules), whose stops end the run. With a plan, take `<branch>` as `executing-task-docs` Preflight 2 derives it from the plan and search main's merges as `delivering-task-queue` Input 3 does, with no question: a match is recorded `NN | delivered <sha7> | <plan> | <sha7>` at once; list its leftovers as Input 3 does, acting on none, and go to the next stage. No match, and the branch, worktree, window, brief or status exists under the names `executing-task-docs` derives: settle the stage as `delivering-task-queue` Input 5–6 settle a unit (ownership proof, then resume or discard); an unproven leftover stops the run as Input 5 says. For a stage whose plan is stale by Freshness, as step 3 judges it, Input 6's question keeps both options and its text but recommends discard, saying why: a resume stops the run at step 3 until the plan is restored to the bytes its mark names; otherwise Input 6's own recommendations apply unchanged. The user may still answer resume.
2. **Plan.** No plan: `NN | planning | - | -`; perform `planning-task-docs` with `<spec>`, Input through Report, with the planner settings. The plan its Report names must match stage `NN` by Stage matching; otherwise stop the run, naming the plan and stage `NN`.
3. **Refine.** A stage step 1 chose to resume whose plan is stale by Freshness stops the run before any refine: `NN | failed: resumed stage with a stale plan | <plan> | -`, naming the stage, the plan and the branch; the way out is a rerun answering discard (the plan is then reviewed and the stage delivered from a fresh branch), or restoring the plan to the bytes its mark names and rerunning to resume. A plan stale by Freshness: `NN | refining | <plan> | -`; perform `refining-task-docs` with `<plan>` only, Input through Report, with the refiner settings and the reviewer flags, then Stage list 2's re-read. `refining-task-docs` adds the plan's spec to its run and, when the spec is stale by Freshness, reviews it beside the plan, by its own Input 2 and 4; this skill neither asks for that review nor prevents it, and the re-read applies as after any refine. A fresh plan: read stage `NN`'s `**Scope:**` and `**Done when:**` lines by the Parsing rules in `git -C <docs repository> show <mark commit>:<spec path relative to it>`, the mark commit being the one its `Review:` line names, and compare them with the current ones. Equal: go on. Different, absent there or unreadable: stop the run, naming stage `NN` and the plan: the plan was reviewed against another stage contract; remove the plan to have the stage planned again, or edit it so that it is stale and reviewed on the rerun.
4. **Deliver.** `NN | delivering | <plan> | -`. Decide the mode and settings as `delivering-task-queue` Preflight 4 does for a unit: a fresh stage takes an explicit `--execution` when given, else `executing-task-docs` [Execution mode](../executing-task-docs/SKILL.md#execution-mode) on the plan, passed as caller-decided (source `rule`), and every field not set explicitly takes the policy value of the mode's role from Preflight 3, the inline effort by that section's rule; a resumed stage keeps its brief's recorded mode and settings, and an explicit `--execution` different from that mode, or given for a legacy brief, stops the run, naming the stage. Perform `delivering-task` with `<plan> --spec <spec>`, plus `--resume` when step 1 chose resume, Execute and then Merge and Cleanup, with the agent, that mode and settings, and the reviewer flags.
5. **Record.** `NN | delivered <sha7> | <plan> | <sha7>`; keep the follow-ups path and count from `delivering-task`'s report for End; go to the next stage. A Cleanup failure after a successful merge still records `delivered <sha7>`, is reported and ends the run.

A sub-skill that refuses, stops, or ends `failed` or `blocked` without the user's answer ends the run at that stage: `failed: <skill>: <reason>`, or `stopped by the user`; a stop of this skill's own is `failed: <reason>` naming its rule ([States](references/state-file.md#states)), on the line of the stage the loop is at (the spec line for Stage list 1's unstaged-plan stop), and a delivered line it names stays as it is. Nothing is undone: window, worktree, branch, status and documents stay as that skill leaves them, and later stages stay `pending`. Go to End. A rerun derives every state again and continues at that stage from what exists.

## End

Report:

- A table `stage | name | plan | state | merge SHA | follow-ups count` from the stage lines; a stage delivered before this run has follow-ups count `-`. A run that ended on the spec line reports that line instead. A run stopped in Preflight 1–3 reports only that stop: its message (the refusal, the failed rule or the unavailable evidence), with no table: nothing ran and no state file was created.
- One settings line per role resolved (`planner`, `refiner`, `implementer`, `inline implementer`): model and effort with the source of each, and the child settings check outcome of each run of that role as its sub-skill reported it, or `not launched`; a resumed stage's run shows its brief's recorded settings, as `delivering-task`'s report gives them; then the reviewer settings line.
- The remaining follow-ups: every existing follow-ups file (`<plan-stem>-follow-ups.md` beside the plan) of the stage plans this run found or wrote, with its count of `- ` lines, for `delivering-task-follow-ups <follow-ups file>...` on what no stage absorbed.
- Every stage never started, with its reason; after a stop, the skill or rule that stopped the run and where to look (the status file, window and worktree that skill names); and the leftovers step 1 listed.
