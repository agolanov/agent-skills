# Delivering Spec Stages

For each clean/path gate and continuation below and in child briefs, use the four ordinary Git commands and identity checks in [checkout state](../independent-review/references/checkout-state.md#direct-use-preflight), with process-local `GIT_OPTIONAL_LOCKS=0`, actual exits and raw output files. A clean gate requires successful commands and empty status and diffs; path gates parse NUL-delimited status and compare exact repository-relative paths, including both rename paths. Failed or unavailable Git evidence stops the dependent action. Use ordinary Git for other read-only checks, retaining real exits. Evidence has the reference's ignored/untracked-content, Git flags/normalization, nested-repository and transient-write limits. Stage/commit only owned paths; write, merge and push authority stays explicit.


`delivering-spec-stages <spec> [--run inline|background|window] [--agent claude|codex] [--impl solo|subagents|direct] [--model M|cli-default] [--effort E|cli-default] [--reviewer-run background|window] [--reviewer-model M|cli-default] [--reviewer-effort E|cli-default] [--reviewer-agent claude|codex] [--reviewer-dual] [--auto]`

The root writes no code and no document. It runs every stage's plan, review and delivery as a [nested call](#nested-calls): `planning-task-docs`, `refining-task-docs` or `delivering-task`, whose Prepare and Accept are performed by short phase agents while this session holds the waits. The root reads none of them; the rules it shares with them are its own display copies under `references/`. It decides what runs next and with which arguments, records stage states in its [state file](references/state-file.md), and reports. Its own questions are those of [stage-derivation.md](references/stage-derivation.md), asked in Stage loop step 1; every other question of a run is a nested call's, relayed to the user. Under `--auto` every question, its own and the nested calls', is routed by child-sessions' [auto.md](../child-sessions/references/auto.md#deciding) instead, every brief says `Auto: yes`, and End lists `## Decisions`.

`--run` places the orchestrator itself: by default (`inline`) this session runs it; `background` or `window` moves it to a child ([Run elsewhere](#run-elsewhere)). `subagent` is not a place for it, since the orchestrator must last through its workers' waits; it and any other value stop before anything starts, naming the value. Every other key goes to the nested calls as given:

- `--agent`: to every nested call. Without it none is passed: a nested call's phase agents are this session's system, which each nested skill then takes as its own.
- `--model`, `--effort` and `--impl`: to every `delivering-task` call, `--model` and `--effort` as explicit implementer values.
- `--reviewer-run`, `--reviewer-model`, `--reviewer-effort`, `--reviewer-agent claude|codex` and `--reviewer-dual`: to every `refining-task-docs` and `delivering-task` call. `--reviewer-run subagent` is refused before anything starts, naming `background` and `window`: a native subagent has no native review command. Refused before anything starts too, naming the key and its value: `--reviewer-agent` with a value other than `claude` or `codex`; `--reviewer-agent` together with `--reviewer-dual`; `--reviewer-dual` together with any `--reviewer-model`, `cli-default` included (under the dual review `review-fix-loop` asks which reviewer a `--reviewer-model` is for, and no key says which). These refusals belong to this key list, not to Preflight: under [Run elsewhere](#run-elsewhere) the launcher applies them before launching. The user's words choosing a reviewer ("a dual review by Claude and Codex", "let Claude review it") count as these keys: map them at entry and announce the mapping, then carry the keys themselves, since neither a nested call nor a child sees the words: in the nested calls' arguments and, under Run elsewhere, in `Arguments:`.

Each nested skill resolves its own role defaults, validates the values it receives and decides the implementation mode; the root resolves no settings and decides no mode. The implementer runs in `delivering-task`'s default place unless the user's words set it ("implement without a window"): the root then announces the mapping and passes that place as `--run` to every `delivering-task` call. A child of [Run elsewhere](#run-elsewhere) takes it from its brief's `Implementer place:` line.

## Run elsewhere

Under `--run background` or `window` this session is a thin launcher (run contract [Places](../child-sessions/references/run-contract.md#places)) and performs none of the sections below: a child of this session's system performs this skill `inline`, its nested calls included, and this session writes its brief, launches it, waits, relays its questions and reports its result.

Follow child-sessions' [Thin launchers](../child-sessions/references/run-contract.md#thin-launchers) with these local parameters.

- **Inputs.** Only `background` and `window` move the orchestrator outside `inline`. Resolve the project checkout by the first rule of [spec-checks.md](references/spec-checks.md) and the spec to an absolute path. When the user's words set the implementer's place, announce the mapping now and add `Implementer place: <place> (the user's words)` to the brief. Apply the key list's reviewer refusals before launching, and map the user's words choosing a reviewer to the keys, announced, so that `Arguments:` carries the keys.
- **Worker and arguments.** Role `orchestrator`, with every field taking the role default. Consume only `--run`; `Arguments:` holds the absolute spec and every other key as given, including `--model` and `--effort`, which set the implementer. `Checkout:` is the project checkout.
- **Name.** `stages-<spec-stem>`, with `<spec-stem>` as [state-file.md](references/state-file.md#names) names it.
- **Authority.** What this skill and its nested calls do with these arguments: windows, documents, commits, merges into main and cleanup, nothing more. The child keeps this skill's nested-call implementation, settings policy and inline fallback.
- **Questions and result.** Stage loop step 1's and every nested call's questions follow the shared window/blocked routing. The child writes `STATUS: done` once it has reported, or `STATUS: failed` with the reason when it stopped, and its End report under `## Report` after the status contract's sections. Report that `## Report` as this skill's End report (after `failed`, the failure and what the status lists), with the shared launch evidence.

## Preflight

1. **Spec.** Take from [spec-checks.md](references/spec-checks.md) its project checkout and docs repository rules, its "no such file" stop, classification rules 1–3 (a plan or anything else is refused as there) and spec checks 1–3, every stop coming before anything runs. Check 2 only locates the file and reads nothing; check 3 runs `stages_parse` from [stages-parse.md](references/stages-parse.md#recipes), the display copy of that file's Recipes. Read check 3's `stages_parse` exits for this skill: exit 0 is a staged spec, the normal case; exit 1 with `no "## Stages"` is an unstaged spec, refused before anything runs, naming the spec: "no `## Stages` section; run `splitting-spec-into-stages <spec>` first"; any other exit 1 stops, naming the failed rule (the stderr line and the Parsing rule that words it); exit 2 stops as unavailable evidence. The splitter's checks 4–6 are not taken: a staged spec's plans are judged by Stage list 1's Unstaged plan check and by the Stage loop, and its Review mark is not checked: a stale or unmarked staged spec proceeds as it is. Then require the project checkout and the docs repository each on its main branch, each by a four-command boundary; uncommitted changes are allowed and stay untouched. This skill commits nothing itself: stage plans are committed by `planning-task-docs`, and the spec is neither committed nor reviewed here: `delivering-task` commits it when it delivers a stage.
2. **Skills.** Locate the installed `planning-task-docs`, `refining-task-docs` and `delivering-task` SKILL.md files by absolute path for the nested calls' `Skill:` lines, and read none of them: each phase agent reads only what its phase names. Locate the installed `child-sessions` and read its [run-contract.md](../child-sessions/references/run-contract.md), [brief-writing.md](../child-sessions/references/brief-writing.md), [status-file.md](../child-sessions/references/status-file.md) and [platform-runtime.md](../child-sessions/references/platform-runtime.md), and under `--auto` its [auto.md](../child-sessions/references/auto.md); also child-sessions SKILL.md Wait, Dialogs and Other operations and environment, and [handoff-record.md Waiting](../child-sessions/references/handoff-record.md#waiting). Read launch-settings Child settings check and Places only when a Waiting block carries `Action: start` or `continue`. The preamble's checkout state is `independent-review`'s. A missing one stops before anything runs, named for the user to install. Resolve child-sessions' installed platform entrypoint by absolute path and set `<runtime>` from its `runtime-dir`; a terminal control this skill uses itself (the `close` of [stage-derivation.md](references/stage-derivation.md#leftovers) Input 6) follows the launch's `capabilities <name>`.
3. **Keys.** `--impl direct` stops here, naming the value and the kind: every stage document is a plan. Announce the implementer's place when the user's words set it.
4. **State file.** Create it per [state-file.md](references/state-file.md) with its header; Stage list writes the lines after it.

## Nested calls

Each `planning-task-docs`, `refining-task-docs` and `delivering-task` run below follows run contract [Nested calls](../child-sessions/references/run-contract.md#nested-calls):

1. **Brief.** Write the call brief at [state-file.md Names](references/state-file.md#names)' path for this stage and phase, with the status path absent. Check run contract Earlier runs before renaming earlier files to `<file>-old-<n>`, the smallest unused `n`. Its identity lines are `Skill:` the absolute SKILL.md Preflight 2 located; `Arguments:` those the step names, every path absolute; `Checkout:` the project checkout; `Authority:` what that skill does with those arguments (windows, documents and commits, and for `delivering-task` its merge into main and cleanup), nothing more; `Place: subagent`; `Auto:` yes under `--auto`, else no; `Status file:`. Append the contract's Phase instructions exactly, with absolute auto.md and status-file.md paths. There is no Launch settings or Opened line: phase agents use the host's default settings, neither set nor verified.
2. **Cycle.** Build every phase brief from this session's arguments and state and run the shared contract's cycle: Prepare, the checked waiting block, this session's wait, fresh Accept for each event, and a fresh agent of the phase that asks a question. Expect worker run names: plan starts with `plan-<spec-stem>-<NN>-`; refine is `refine-<plan stem>`; deliver is the branch Stage loop 1 derives. These are never this orchestrator's call names. Read the Report items the Stage loop step names and retain Decisions, the agent counts, worker-place lines and this session's wait/dialog evidence for End. Keep child-sessions' [quiet wait](../child-sessions/SKILL.md#wait) across calls: a call's result goes to the state and the final report, with no message to the user between calls.
3. **Inline fallback.** Use the shared contract's fallback only when this host has no subagent tool or refuses a phase agent's spawn. This call and later calls then run inline, named with the reason in End; read that SKILL.md and perform its phases as a direct run. A call already past Prepare continues from its record as one root, opening no second worker. Its brief and status follow the shared contract's inline rule.

## Stage list

1. **Stage lines.** Derive each stage's state (plan, merge found and leftovers named as Stage loop step 1 finds them, mark fresh or stale as Stage loop step 3 judges it); Stage loop step 1's settling and stops act when the loop reaches the stage. Apply the [display copy](references/stages-section.md#parsing-rules)'s Unstaged plan rule to the spec's candidates: an unstaged plan stops the run on the spec line, `spec | failed: unstaged plan <plan> | - | -`, naming the plan with the rule's message, "staged spec with an unstaged plan; remove or stage the plan". Write the stage lines (`pending`, the plan field the stage's one matching plan or `-`), show the list with each stage's derived state and go on to the Stage loop, with no question.
2. **Re-read.** Before every `refining-task-docs` call in the Stage loop, keep the stage list [`stages_parse`](references/stages-parse.md#recipes) gives; after it, run `stages_parse` again. A section that no longer parses stops the run, naming the failed rule. A stage of the kept list whose `NN<TAB>name` line is gone (renamed, renumbered or removed) stops the run, naming it, when it is delivered (Stage loop step 1 finds its merge) or is the stage the loop is at. Any other change is the new list.

## Stage loop

For each stage `NN` of the current list, in number order:

1. **Derive.** Find the stage's plan by Stage matching of the [display copy](references/stages-section.md#parsing-rules), whose stops end the run. With a plan, take `<branch>` and the window name from the plan by [Branch and window](references/stage-derivation.md#branch-and-window) and search main's merges by [Merged](references/stage-derivation.md#merged), with no question: a match is recorded `NN | delivered <sha7> | <plan> | <sha7>` at once; list its leftovers as that section does, acting on none, and go to the next stage. No match, and the branch, worktree, window, brief or status exists under those names: settle the stage as [Leftovers](references/stage-derivation.md#leftovers) Input 5–6 settle a unit (ownership proof, then resume or discard), Input 6's question being this skill's own and its discard or archive performed at once; an unproven leftover stops the run as Input 5 says. For a stage whose plan is stale by [Freshness](references/review-mark.md#freshness), as step 3 judges it, Input 6's question keeps both options and its text but recommends discard, saying why: a resume stops the run at step 3 until the plan is restored to the bytes its mark names; otherwise Input 6's own recommendations apply unchanged. The user may still answer resume.
2. **Plan.** No plan: `NN | planning | - | -`; nested call `planning-task-docs <spec>`, with `--agent` when given. Read from its Report the spec and plan paths and the stage number. The plan must match stage `NN` by Stage matching; otherwise stop the run, naming the plan and stage `NN`.
3. **Refine.** A stage step 1 chose to resume whose plan is stale by Freshness stops the run before any refine: `NN | failed: resumed stage with a stale plan | <plan> | -`, naming the stage, the plan and the branch; the way out is a rerun answering discard (the plan is then reviewed and the stage delivered from a fresh branch), or restoring the plan to the bytes its mark names and rerunning to resume. A plan stale by Freshness: `NN | refining | <plan> | -`; nested call `refining-task-docs <plan>`, the plan only, with `--agent` and the reviewer flags when given, then Stage list 2's re-read. Read from its Report each document's mark state (its new `Review:` line, `fresh, context only` or `not marked: <why>`) and the open findings, for End; the stage goes on to step 4 whatever the mark state. `refining-task-docs` adds the plan's spec to its run by its own rules and may review it beside the plan; this skill neither asks for that review nor prevents it, and the re-read applies as after any refine. A fresh plan: read stage `NN`'s `**Scope:**` and `**Done when:**` lines by the Parsing rules in `git -C <docs repository> show <mark commit>:<spec path relative to it>`, the mark commit being the one its `Review:` line names, and compare them with the current ones. Equal: go on. Different, absent there or unreadable: stop the run, naming stage `NN` and the plan: the plan was reviewed against another stage contract; remove the plan to have the stage planned again, or edit it so that it is stale and reviewed on the rerun.
4. **Deliver.** `NN | delivering | <plan> | -`. Nested call `delivering-task <plan> --spec <spec>`, plus `--resume` when step 1 chose resume, with `--agent`, `--impl`, `--model`, `--effort` and the reviewer flags when given, and `--run` with the implementer's place when the user's words or the brief's `Implementer place:` line set it. `delivering-task` decides the mode and resolves the implementer's settings itself; a resumed stage keeps its brief's recorded mode and settings by `delivering-task`'s resume path, which stops on an explicit value that differs. Read from its Report the merge SHA, the follow-ups path and count, and its implementation mode and settings lines.
5. **Record.** `NN | delivered <sha7> | <plan> | <sha7>`; keep the follow-ups path and count and the settings lines for End; go to the next stage. A Cleanup failure after a successful merge (a `failed` call whose Report names the merge SHA) still records `delivered <sha7>`, is reported and ends the run.

A nested call that ends `failed` (the nested skill refused or stopped), or `blocked` while the user gives no answer, ends the run at that stage: `failed: <skill>: <reason>`, or `stopped by the user`. A stop of this skill's own is `failed: <reason>` naming its rule ([States](references/state-file.md#states)), on the line of the stage the loop is at (the spec line for Stage list 1's unstaged-plan stop), and a delivered line it names stays as it is. Nothing is undone: window, worktree, branch, status and documents stay as that skill leaves them, and later stages stay `pending`. Go to End. A rerun derives every state again from Git and the documents and continues at that stage from what exists, including after a stop inside a phase cycle. A planner's or refiner's live window is that skill's own refusal when its call runs again: the user finishes or closes it first. A delivery's branch/worktree is settled by Stage loop 1's resume-or-discard rules. Earlier runs' question must be settled before taking a possibly live call's files or putting another watcher on its child.

## End

Report:

- A table `stage | name | plan | state | merge SHA | follow-ups count` from the stage lines; a stage delivered before this run has follow-ups count `-`. A run that ended on the spec line reports that line instead. A run stopped in Preflight 1–3 reports only that stop: its message (the refusal, the failed rule or the unavailable evidence), with no table: nothing ran and no state file was created.
- The settings lines each nested call's Report gave, by stage: the planner's; the refiner's with its Reviewer settings, Reviewer run and Reviewer agent lines; the delivery's implementation mode line and its implementer and reviewer settings lines (the Reviewer agent line included), a resumed stage's showing its brief's recorded settings. Then for each call: phase agents: `subagent`, the host's default settings, not verified; `<p>` Prepare and `<a>` Accept agents. Add this session's own `Wait:` line and dialog counts (answered, declined, escalated), each worker whose inline place ran as `subagent`, and each call that ran `inline` with the shared contract's fallback reason.
- Each refine's mark states and open findings, as its Report gave them.
- The remaining follow-ups: every existing follow-ups file (`<plan-stem>-follow-ups.md` beside the plan) of the stage plans this run found or wrote, with its count of `- ` lines, for `delivering-task-follow-ups <follow-ups file>...` on what no stage absorbed.
- Under `--auto`, the `## Decisions` of [auto.md](../child-sessions/references/auto.md#decisions): this session's own and those of every nested call's status.
- Every stage never started, with its reason; after a stop, the skill or rule that stopped the run and where to look (the nested call's brief and status file, and the status file, window and worktree its Report names); and the leftovers step 1 listed.
