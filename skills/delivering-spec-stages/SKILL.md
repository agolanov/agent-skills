# Delivering Spec Stages

For each clean/path gate and continuation below and in child briefs, use the four ordinary Git commands and identity checks in [checkout state](../independent-review/references/checkout-state.md#direct-use-preflight), with process-local `GIT_OPTIONAL_LOCKS=0`, actual exits and raw output files. A clean gate requires successful commands and empty status and diffs; path gates parse NUL-delimited status and compare exact repository-relative paths, including both rename paths. Failed or unavailable Git evidence stops the dependent action. Use ordinary Git for other read-only checks, retaining real exits. Evidence has the reference's ignored/untracked-content, Git flags/normalization, nested-repository and transient-write limits. Stage/commit only owned paths; write, merge and push authority stays explicit.


`delivering-spec-stages <spec> [--run inline|background|window] [--agent claude|codex] [--execution inline|subagents|direct] [--model M|cli-default] [--effort E|cli-default] [--reviewer-run background|subagent|window] [--reviewer-model M|cli-default] [--reviewer-effort E|cli-default] [--auto]`

The root writes no code and no document. It runs every stage's plan, review and delivery as a [nested call](#nested-calls): `planning-task-docs`, `refining-task-docs` or `delivering-task` performed completely by a subagent, which reads that skill. The root reads none of them; the rules it shares with them are its own display copies under `references/`. It decides what runs next and with which arguments, records stage states in its [state file](references/state-file.md), and reports. Its own questions are those of [stage-derivation.md](references/stage-derivation.md), asked in Stage loop step 1; every other question of a run is a nested call's, relayed to the user. Under `--auto` every question, its own and the nested calls', is routed by child-sessions' [auto.md](../child-sessions/references/auto.md#deciding) instead, every brief says `Auto: yes`, and End lists `## Decisions`.

`--run` places the orchestrator itself: by default (`inline`) this session runs it; `background` or `window` moves it to a child ([Run elsewhere](#run-elsewhere)). `subagent` is not a place for it, since its nested calls are subagents; it and any other value stop before anything starts, naming the value. Every other key goes to the nested calls as given:

- `--agent`: to every nested call. Without it none is passed: a nested call's subagent is this session's system, which each nested skill then takes as its own.
- `--model`, `--effort` and `--execution`: to every `delivering-task` call, `--model` and `--effort` as explicit implementer values.
- `--reviewer-run`, `--reviewer-model` and `--reviewer-effort`: to every `refining-task-docs` and `delivering-task` call.

Each nested skill resolves its own role defaults, validates the values it receives and decides the execution mode; the root resolves no settings and decides no mode. The implementer runs in `delivering-task`'s default place unless the user's words set it ("implement without a window"): the root then announces the mapping and passes that place as `--run` to every `delivering-task` call. A child of [Run elsewhere](#run-elsewhere) takes it from its brief's `Implementer place:` line.

## Run elsewhere

Under `--run background` or `window` this session is a thin launcher (run contract [Places](../child-sessions/references/run-contract.md#places)) and performs none of the sections below: a child of this session's system performs this skill `inline`, its nested calls included, and this session writes its brief, launches it, waits, relays its questions and reports its result.

Follow child-sessions' [Thin launchers](../child-sessions/references/run-contract.md#thin-launchers) with these local parameters.

- **Inputs.** Only `background` and `window` move the orchestrator outside `inline`. Resolve the project checkout by the first rule of [spec-checks.md](references/spec-checks.md) and the spec to an absolute path. When the user's words set the implementer's place, announce the mapping now and add `Implementer place: <place> (the user's words)` to the brief.
- **Worker and arguments.** Role `orchestrator`, with every field taking the role default. Consume only `--run`; `Arguments:` holds the absolute spec and every other key as given, including `--model` and `--effort`, which set the implementer. `Checkout:` is the project checkout.
- **Name.** `stages-<spec-stem>`, with `<spec-stem>` as [state-file.md](references/state-file.md#names) names it.
- **Authority.** What this skill and its nested calls do with these arguments: windows, documents, commits, merges into main and cleanup, nothing more. The child keeps this skill's nested-call implementation, settings policy and inline fallback.
- **Questions and result.** Stage loop step 1's and every nested call's questions follow the shared window/blocked routing. The child writes `STATUS: done` once it has reported, or `STATUS: failed` with the reason when it stopped, and its End report under `## Report` after the status contract's sections. Report that `## Report` as this skill's End report (after `failed`, the failure and what the status lists), with the shared launch evidence.

## Preflight

1. **Spec.** Take from [spec-checks.md](references/spec-checks.md) its project checkout and docs repository rules, its "no such file" stop, classification rules 1–3 (a plan or anything else is refused as there) and spec checks 1–3, every stop coming before anything runs. Check 2 only locates the file and reads nothing; check 3 runs `stages_parse` from [stages-parse.md](references/stages-parse.md#recipes), the display copy of that file's Recipes. Read check 3's `stages_parse` exits for this skill: exit 0 is a staged spec, the normal case; exit 1 with `no "## Stages"` is an unstaged spec, refused before anything runs, naming the spec: "no `## Stages` section; run `splitting-spec-into-stages <spec>` first"; any other exit 1 stops, naming the failed rule (the stderr line and the Parsing rule that words it); exit 2 stops as unavailable evidence. The splitter's checks 4–6 are not taken: a staged spec's plans are judged by Stage list 1's Unstaged plan check and by the Stage loop, and its Review mark is not checked: a stale or unmarked staged spec proceeds as it is. Then require the project checkout and the docs repository each on its main branch, each by a four-command boundary; uncommitted changes are allowed and stay untouched. This skill commits nothing itself: stage plans are committed by `planning-task-docs`, and the spec is neither committed nor reviewed here: `delivering-task` commits it when it delivers a stage.
2. **Skills.** Locate the installed `planning-task-docs`, `refining-task-docs` and `delivering-task` SKILL.md files by absolute path for the nested calls' `Skill:` lines, and read none of them: each nested call's subagent reads its own. Locate the installed `child-sessions` and read its [run-contract.md](../child-sessions/references/run-contract.md), [brief-writing.md](../child-sessions/references/brief-writing.md), [status-file.md](../child-sessions/references/status-file.md) and [platform-runtime.md](../child-sessions/references/platform-runtime.md), and under `--auto` its [auto.md](../child-sessions/references/auto.md); the preamble's checkout state is `independent-review`'s. A missing one stops before anything runs, named for the user to install. Resolve child-sessions' installed platform entrypoint by absolute path and set `<runtime>` from its `runtime-dir`; a terminal control this skill uses itself (the `close` of [stage-derivation.md](references/stage-derivation.md#leftovers) Input 6) follows the launch's `capabilities <name>`.
3. **Keys.** `--execution direct` stops here, naming the value and the kind: every stage document is a plan. Announce the implementer's place when the user's words set it.
4. **State file.** Create it per [state-file.md](references/state-file.md) with its header; Stage list writes the lines after it.

## Nested calls

Each `planning-task-docs`, `refining-task-docs` and `delivering-task` run below is a nested call by run contract [Nested calls](../child-sessions/references/run-contract.md#nested-calls):

1. **Brief.** Write it at the brief path [state-file.md](references/state-file.md#names) names for the stage and phase, the status path beside it absent; an earlier run's file at either path is renamed `<file>-old-<n>` first, `n` the smallest unused number, after the check of run contract [Earlier runs](../child-sessions/references/run-contract.md#earlier-runs). It holds the run contract identity lines: `Skill:` the SKILL.md Preflight 2 located; `Arguments:` those the step names, every path absolute; `Checkout:` the project checkout; `Authority:` what that skill does with these arguments (its windows, documents and commits, and for `delivering-task` its merge into main and its cleanup), nothing more; `Place: subagent`; `Auto:` `yes` under `--auto`, else `no`; `Status file:`. It has no `Launch settings:` or `Opened:` line: a nested call takes the host's default settings, neither set nor verified, as run contract Nested calls says. Then these instructions, with the absolute status-file.md and auto.md paths filled in:

   ```text
   Read the Skill completely and perform it in this session with the Arguments as given, plus --auto when Auto is yes, within the Authority; add no other key, so that its workers take the places its Arguments and its own defaults give them. When Auto is yes, follow <absolute auto.md> as a child and write every decision of the call under the status's ## Decisions. Run the skill completely, its windows included, and write its Report under a status section ## Report, after the status contract's sections. Write the status file by <absolute status-file.md>: STATUS: done once the skill has reported, STATUS: failed with the reason when it refused or stopped. Ask nobody directly: a question ends your turn with STATUS: blocked, its Questions holding the question, the options and your recommendation. End every turn with the status file written and its exact first line as your last message.
   Before the skill opens its first window, check that your shell tool can hold child-sessions' foreground wait (its foreground timeout reaches the wait's, or a yielded call can be polled until it exits). When it cannot, when a wait is refused or cut off before its timeout, when the host refuses a subagent the skill starts, or when the skill refuses a combination because this session is a subagent, stop there and write STATUS: failed whose reason starts "cannot hold the call:", naming what happened and every window, worktree and branch the skill left.
   ```
2. **Run.** Start a fresh subagent with the brief by the `subagent` bullet of run contract [Launch and wait](../child-sessions/references/run-contract.md#launch-and-wait), setting no model or effort, and wait until it ends. A subagent that ends without a valid first status line gets that section's one restart.
3. **Status.** `done`: read from `## Report` the items the step names. `blocked`: show the user its Questions verbatim with options and recommendation, obtain the answer and continue the same subagent by run contract [Questions and continuation](../child-sessions/references/run-contract.md#questions-and-continuation). Under `--auto` route the question by [auto.md](../child-sessions/references/auto.md#deciding) instead, then continue the same subagent with the answer the same way. Keep each status's `## Decisions` for the final report. `failed`: the nested skill refused or stopped; its reason and `## Report` go to the step's failure rule.
4. **Inline fallback.** A call the host cannot hold in a subagent runs `inline`: this session reads that SKILL.md then and performs it with the same arguments, as a direct run of that skill does, and End names the call and why. The host cannot hold it when it has no subagent tool; when Codex's `[agents] max_depth` in the user's `config.toml` leaves no level below this session for the call's subagent, or for a subagent the nested skill's root itself starts (an implementer the user's words placed in `subagent`); when the host refuses the spawn; or when the call's status reason starts `cannot hold the call:`. Run contract [Host mechanisms](../child-sessions/references/run-contract.md#host-mechanisms) records a nested start and a subagent holding the wait loop as `unverified` on both hosts: attempt the subagent, fall back on a refused spawn or a `cannot hold the call:` status, and name the mechanism unverified in End. After a fallback, later calls run `inline` at once for the same reason. A `cannot hold the call:` status naming a live window, a worktree or a branch the call left is not rerun: the run ends at that stage as a failed call does, naming those leftovers, which stay as they are (a rerun settles a delivery's leftovers by Stage loop step 1; a planner's or refiner's window is the user's to finish or close first).

## Stage list

1. **Stage lines.** Derive each stage's state (plan, merge found and leftovers named as Stage loop step 1 finds them, mark fresh or stale as Stage loop step 3 judges it); Stage loop step 1's settling and stops act when the loop reaches the stage. Apply the [display copy](references/stages-section.md#parsing-rules)'s Unstaged plan rule to the spec's candidates: an unstaged plan stops the run on the spec line, `spec | failed: unstaged plan <plan> | - | -`, naming the plan with the rule's message, "staged spec with an unstaged plan; remove or stage the plan". Write the stage lines (`pending`, the plan field the stage's one matching plan or `-`), show the list with each stage's derived state and go on to the Stage loop, with no question.
2. **Re-read.** Before every `refining-task-docs` call in the Stage loop, keep the stage list [`stages_parse`](references/stages-parse.md#recipes) gives; after it, run `stages_parse` again. A section that no longer parses stops the run, naming the failed rule. A stage of the kept list whose `NN<TAB>name` line is gone (renamed, renumbered or removed) stops the run, naming it, when it is delivered (Stage loop step 1 finds its merge) or is the stage the loop is at. Any other change is the new list.

## Stage loop

For each stage `NN` of the current list, in number order:

1. **Derive.** Find the stage's plan by Stage matching of the [display copy](references/stages-section.md#parsing-rules), whose stops end the run. With a plan, take `<branch>` and the window name from the plan by [Branch and window](references/stage-derivation.md#branch-and-window) and search main's merges by [Merged](references/stage-derivation.md#merged), with no question: a match is recorded `NN | delivered <sha7> | <plan> | <sha7>` at once; list its leftovers as that section does, acting on none, and go to the next stage. No match, and the branch, worktree, window, brief or status exists under those names: settle the stage as [Leftovers](references/stage-derivation.md#leftovers) Input 5–6 settle a unit (ownership proof, then resume or discard), Input 6's question being this skill's own; an unproven leftover stops the run as Input 5 says. For a stage whose plan is stale by [Freshness](references/review-mark.md#freshness), as step 3 judges it, Input 6's question keeps both options and its text but recommends discard, saying why: a resume stops the run at step 3 until the plan is restored to the bytes its mark names; otherwise Input 6's own recommendations apply unchanged. The user may still answer resume.
2. **Plan.** No plan: `NN | planning | - | -`; nested call `planning-task-docs <spec>`, with `--agent` when given. Read from its Report the spec and plan paths and the stage number. The plan must match stage `NN` by Stage matching; otherwise stop the run, naming the plan and stage `NN`.
3. **Refine.** A stage step 1 chose to resume whose plan is stale by Freshness stops the run before any refine: `NN | failed: resumed stage with a stale plan | <plan> | -`, naming the stage, the plan and the branch; the way out is a rerun answering discard (the plan is then reviewed and the stage delivered from a fresh branch), or restoring the plan to the bytes its mark names and rerunning to resume. A plan stale by Freshness: `NN | refining | <plan> | -`; nested call `refining-task-docs <plan>`, the plan only, with `--agent` and the reviewer flags when given, then Stage list 2's re-read. Read from its Report each document's mark state (its new `Review:` line, `fresh, context only` or `not marked: <why>`) and the open findings, for End; the stage goes on to step 4 whatever the mark state. `refining-task-docs` adds the plan's spec to its run by its own rules and may review it beside the plan; this skill neither asks for that review nor prevents it, and the re-read applies as after any refine. A fresh plan: read stage `NN`'s `**Scope:**` and `**Done when:**` lines by the Parsing rules in `git -C <docs repository> show <mark commit>:<spec path relative to it>`, the mark commit being the one its `Review:` line names, and compare them with the current ones. Equal: go on. Different, absent there or unreadable: stop the run, naming stage `NN` and the plan: the plan was reviewed against another stage contract; remove the plan to have the stage planned again, or edit it so that it is stale and reviewed on the rerun.
4. **Deliver.** `NN | delivering | <plan> | -`. Nested call `delivering-task <plan> --spec <spec>`, plus `--resume` when step 1 chose resume, with `--agent`, `--execution`, `--model`, `--effort` and the reviewer flags when given, and `--run` with the implementer's place when the user's words or the brief's `Implementer place:` line set it. `delivering-task` decides the mode and resolves the implementer's settings itself; a resumed stage keeps its brief's recorded mode and settings by `delivering-task`'s resume path, which stops on an explicit value that differs. Read from its Report the merge SHA, the follow-ups path and count, and its execution mode and settings lines.
5. **Record.** `NN | delivered <sha7> | <plan> | <sha7>`; keep the follow-ups path and count and the settings lines for End; go to the next stage. A Cleanup failure after a successful merge (a `failed` call whose Report names the merge SHA) still records `delivered <sha7>`, is reported and ends the run.

A nested call that ends `failed` (the nested skill refused or stopped), or `blocked` while the user gives no answer, ends the run at that stage: `failed: <skill>: <reason>`, or `stopped by the user`; a `cannot hold the call:` status is no failure but [Nested calls](#nested-calls) 4's fallback, unless it names leftovers. A stop of this skill's own is `failed: <reason>` naming its rule ([States](references/state-file.md#states)), on the line of the stage the loop is at (the spec line for Stage list 1's unstaged-plan stop), and a delivered line it names stays as it is. Nothing is undone: window, worktree, branch, status and documents stay as that skill leaves them, and later stages stay `pending`. Go to End. A rerun derives every state again and continues at that stage from what exists.

## End

Report:

- A table `stage | name | plan | state | merge SHA | follow-ups count` from the stage lines; a stage delivered before this run has follow-ups count `-`. A run that ended on the spec line reports that line instead. A run stopped in Preflight 1–3 reports only that stop: its message (the refusal, the failed rule or the unavailable evidence), with no table: nothing ran and no state file was created.
- The settings lines each nested call's Report gave, by stage: the planner's; the refiner's with its Reviewer settings and Reviewer run lines; the delivery's execution mode line and its implementer and reviewer settings lines, a resumed stage's showing its brief's recorded settings. Then one line for the nested calls themselves: `subagent` with the host's default settings, not verified, and each call that ran `inline` with its reason and the `unverified` host mechanism it met.
- Each refine's mark states and open findings, as its Report gave them.
- The remaining follow-ups: every existing follow-ups file (`<plan-stem>-follow-ups.md` beside the plan) of the stage plans this run found or wrote, with its count of `- ` lines, for `delivering-task-follow-ups <follow-ups file>...` on what no stage absorbed.
- Under `--auto`, the `## Decisions` of [auto.md](../child-sessions/references/auto.md#decisions): this session's own and those of every nested call's status.
- Every stage never started, with its reason; after a stop, the skill or rule that stopped the run and where to look (the nested call's brief and status file, and the status file, window and worktree its Report names); and the leftovers step 1 listed.
